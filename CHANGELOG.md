# Changelog

[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project
uses tag-based releases (see the `v*` tags in the repository).

## [Unreleased]

### Added

- **A role can now be created FOR a tenant, and a role that belongs to every tenant finally says so (#888, #886).** An operator reported that "roles are deployment wide and a role edited in a tenant affects the same named role in another tenant". There is **no cross-tenant write bug** — `roleManageableByTenant()` matches only `WHERE r.id = ? AND r.tenant_id = ?`, so a tenant's write against a global role does not match and returns 404, and that is unchanged here. But the reporter's experience was real, and it had two causes that produce each other. `POST /api/roles` wrote `TenantContext::getTenantId()` unconditionally; the platform is administered **from the system tenant (0)**, so every role an operator ever created was stamped tenant 0 — and a tenant-0 role is OWNED by the system tenant, invisible to every other tenant. There was no way to say "this role belongs to tenant 7", and no way to create a shared one either: only the seeder ever wrote a `tenant_id IS NULL` row. So the only roles anybody could actually use were the three seeded global ones, every role in the list was deployment-wide, and the list rendered a global base role and a tenant's own identically. On the live staging install that is exactly what had happened: **zero tenant-owned roles, all three global.**
  - **The create contract: `tenant_id` for a named tenant, `global: true` for a shared one, both honoured only for a tenant-0 caller, both absent by default.** Absent means the caller's own tenant, so every existing client sends a byte-identical request and nothing that works today changes. This is the pattern `POST /api/users/{id}/memberships` established in v0.2.1, deliberately down to the reasoning for widening the endpoint that already manipulates the thing rather than overloading a neighbour: the contract stays "create a role here", with cross-tenant creation as an explicitly authorised parameter and not a second meaning bolted onto the same call. An explicit field from a caller who may not use it is a **403, not a silent ignore** — a field that is accepted and quietly discarded teaches the caller it worked, and here "it worked" would mean a role in the wrong tenant.
  - **Explicit global is a SEPARATE field, and `tenant_id` is integer-only.** The tempting spelling was `tenant_id: null`, and it was rejected. Ownership has three states, and over HTTP an omitted field and an explicit null are not reliably distinguishable *by clients*: `JSON.stringify` drops `undefined`, a form's empty select sends `null`, and a typed client's optional field may do either. Overloading null would make which tenant a role lands in depend on a serialiser's habits — the same omitted-vs-null trap that made resource-grant revoke id-addressed in v0.2.2. So `null` and `''` are a **400 that names `global`**, rather than a synonym for absent (a deliberate divergence from the more tolerant membership parameter, which has no third state to confuse), and sending both fields is a 400 rather than a precedence rule nobody reads until it has already written the wrong row. The alternative — one nullable field — would have cost a contract whose meaning is decided by the client library, and a class of mis-scoped role that is invisible in the request log because the field simply was not there.
  - **Uniqueness follows the target, not the caller.** Role names are unique per tenant since migration 093, and the 409 is that rule read from the caller's side — so a cross-tenant create moves which side that is. Creating "Supervisor" for tenant 7 is checked against tenant 7's namespace plus the global base names it inherits, never the operator's own; a `global: true` create is checked against the global namespace **alone**, so a tenant's private role name cannot stop the operator naming a base role. A named tenant that does not exist is a **404, not a 403**, matching how an invisible role is answered everywhere else in this handler, so the status code never becomes the thing that discloses existence.
  - **Ownership is settled at create and never moves.** `PATCH` gained no tenant field. Re-homing a role would silently revoke it from everyone holding it in the old tenant, which is a different operation with a different blast radius from "rename this role", and one endpoint should not quietly do both.
  - **`global` is a new flag on every role payload, and it could not have been `manageable`.** The list already carried `manageable` (WC-222) and the record page a "Global base role" badge (#885) — both derived from *whether this caller may write the row*. For the **system tenant that is true of every role**, so the one caller whose edit reaches every tenant was also the one for whom the existing signal said nothing: the record page inferred "global" from `!manageable` and therefore labelled a deployment-wide base role "Your tenant's role" to the operator about to change it. `global` is a fact about the row and is now returned beside `manageable` on list and detail alike. The raw owning `tenant_id` is still never returned — a tenant learns that a role is shared, never who else has one.
  - **The marker goes on the LIST, because the list is where the action starts.** Global rows carry a "Global" badge next to the name, and Edit/Delete stay gated on manageability rather than globality — a tenant-0 operator may still edit a global role, since the point is to inform the decision, not remove it. Before that edit is made, the edit modal, the delete dialog and the record page all say the same thing in plain words: this is one role shared by every tenant on this deployment, and saving changes it for all of them. It is the only edit in the product with deployment-wide blast radius and it had looked like any other.
  - **No new permission, deliberately.** Every `/api/roles/*` route stays on the same `admin` gate. A new slug ships a grant migration that can only reach the seeded `admin` role, so operators running a custom administrative role lose the capability on upgrade and find out as a 403 — which is precisely what #834 documents happening here before. The create picker in the UI is likewise supplied by the host only when the caller is the system tenant, so it is hidden rather than offered and then refused.
  - **Both engines, one file.** The tenancy tests live in `tests/Integration` rather than beside the other roles tests, because CI's PostgreSQL job runs only the Integration and Security suites and everything asserted here is the class of thing that diverges between engines: a NULL written into an integer column, a bound `null` in an `IS NULL` comparison, a non-numeric value bound against `tenants.id` that SQLite shrugs off and PostgreSQL refuses outright. The SQLite job runs the same file through the default suite, so one set of assertions covers both. And RTL was not a pass at the end: all eleven new strings go through the injected translator into the `admin` domain, declared in file-scoped `@i18n-keys` blocks and extracted with `whity-cli i18n:extract`.
- **The version this deployment is actually running is now readable from the two places anyone looks for it — the dashboard and `GET /api/health` — instead of from nowhere at all.** `GET /api/v1/platform/version` has returned `core_version`, `sdk_version` and `php_version` since WHIT-587, and **not one line of UI has ever called it.** The only reference to that path anywhere under `web/` was the generated `schema.d.ts`. So the endpoint built precisely so that an operator without a shell could answer "what am I running?" was answerable only by someone who could open a terminal and curl it — which is the audience it was built to stop needing. The `sdk_version` half was worse off still: it appeared in no surface a human sees, while being the number that explains nearly every "my plugin stopped loading after the upgrade", because that is what a plugin's sdk-constraint is evaluated against. This wires the existing data to a screen and adds one field to the health probe. No new endpoint, no new permission, no new state.
  - **`GET /api/health` gains `sdk_version`, and `version` is untouched.** The probe now answers `{status, version, sdk_version, workers_active, memory_usage_mb, uptime_seconds, db_connected}`. `version` keeps its name rather than becoming `core_version` for symmetry: it is a published field on a public endpoint that load balancers and blackbox probes already parse (`docs/wiki/SLOs-and-Alerting.md` builds the availability SLO on this route), and renaming a key there is a breaking change for monitoring nobody in this repository can see or fix. Both values are computed from constants, so they survive a dead database and are still reported on the 503 degraded response — which is exactly the moment somebody asks which build is misbehaving.
  - **That moves `sdk_version` from `settings:manage` to unauthenticated, deliberately, and it is one line to undo.** `/api/health` is public and rate-limit exempt; `/api/v1/platform/version` is gated on `settings:manage` AND the system tenant. Serving the same number on both means the gate no longer holds it. The judgement is that this is right — monitoring is where a version question is genuinely asked, at an hour when nobody is signing into an admin UI, and the marginal disclosure is small because the core release has been public on this endpoint since WC-172 and the SDK version is derivable from it by anyone holding the public source or a GHCR tag. But it is a judgement, not a consequence, so it is recorded as one: the reasoning sits on `HealthApiHandler`'s docblock next to the field, and **removing the field removes the disclosure and costs no UI**, because the dashboard deliberately does not read versions from there. An operator who disagrees deletes one array entry and one schema property.
  - **The dashboard reads the GATED endpoint, not the newly-public one, and that is the whole design decision.** Sourcing `/admin/stats` from `/api/health` was the tempting option: it is public, so the permission question disappears and every viewer sees a version. It was rejected because the permission question disappearing is the problem, not the fix. `/api/v1/platform/version` is gated the way it is because version state describes the whole DEPLOYMENT — on a shared install that is none of a tenant admin's business, and they have no way to act on it, since updating is a host-level operation. Routing the UI around that gate would be re-deciding an authorization question in the presentation layer, silently, in the opposite direction from the one its author decided. The two calls are also different in kind and stay consistent: the probe discloses to MONITORING, and that is not a back door for disclosing to users the product gates.
  - **Two further reasons the probe is the wrong source for a screen.** `docs/wiki/API-Deprecation-Lifecycle.md` explicitly exempts the unversioned infrastructure routes — `/api/health`, `/api/version`, `/api/openapi.json` — from the deprecation policy, so binding a product surface to a contract documented as free to change without notice is a UI break with no gate to catch it. And `/api/health` is dependency-light on purpose so that it answers while everything else is down; making the admin dashboard a consumer of it turns a liveness probe into a product dependency and adds a reason to be conservative about ever changing it again.
  - **A viewer without the permission gets ABSENCE, and absence is a designed state rather than an unhandled one.** The core and SDK versions render as two rows inside the existing **System** card on `/admin/stats`, above the PHP version already there. A 403 — the ordinary, expected outcome for a tenant admin on a shared install — renders the card without those two rows and otherwise complete. **No error alert, no toast, no `console.error`, and no greyed-out row hinting at a permission they do not have.** Timeouts, network failures and malformed bodies collapse to the identical silence, because the distinction carries no action: a version readout is context, and the page already owns one honest error surface for the data it exists to show. `stats-page-platform-version.test.tsx` drives each failure path separately rather than assuming they are equivalent.
  - **Placing them in the System card instead of a new one is what makes the absence invisible.** That card already answers "what is this deployment running" with the PHP version, so the versions are not a new idea there — and its PHP row is sourced from the wider-gated `/api/v1/admin/stats`, so it is deliberately NOT re-pointed at the narrower endpoint: consolidating the source would have made a row disappear for people who see it today. A fourth card in a three-column grid would also have been the conspicuous option in both directions — a lone card on its own row when present, a visibly missing one when denied. Two rows appearing on the permitted path is the better transition than two rows collapsing on the denied path, so they render only once resolved, with no `--` placeholder: a placeholder makes "still loading" and "you may not read this" look identical right up until one of them vanishes.
  - **Kept as two requests rather than folded into the stats payload.** The dashboard's own data needs the `admin` role; version state needs `settings:manage` plus the system tenant. Merging them forces one of the two gates to move — either the dashboard narrows to the operator gate or deployment state widens to every tenant admin — so they stay independent in both directions, and a wedged stats query no longer takes the version readout down with it.
  - **`HealthResponse` documented a `worker_count` the server has never sent.** The handler has always returned `workers_active`. Corrected while adding `sdk_version` beside it rather than left alone: a spec naming a key the server does not send is worse than one omitting it, because the generated client compiles and fails at runtime. Both typed clients (`web/lib/api/schema.d.ts`, `packages/api-client/src/schema.d.ts`) are regenerated, and `docs/wiki/Core-Update.md`'s three-version table now lists both places the SDK version can be read.
  - All new labels go through the translator into the `admin` domain and are extracted with `whity-cli i18n:extract`; the version strings themselves render verbatim, because a version is a value and not source copy. The System card's subtitle moves from "Resource Usage" to "Versions and resource usage", which was already inaccurate the moment a PHP version was listed under it.
- **A role grant and a role revocation are now in the audit trail, recorded against the PERSON whose authority changed (#889).** `user.membership.added` and `user.membership.removed` were dispatched as hook events and were simply not in `AuditLogger::subscribe()`'s map, which covered role/user/tenant/OU CRUD and OU role changes only — so nothing wrote them down. Because a revocation DELETES the membership row, the consequence was that the platform could say who holds a role now and never who used to: **"who removed this person's access, and when" was unanswerable**, including for an operator investigating an incident. #885 had to write that limitation into its own docblock rather than guess at the fix.
  - **The target is the USER, and the `ou.role_assigned` precedent argues FOR that rather than against it.** An audit row names an actor, an action and one target, and a membership change has two candidates with only one `target_type`/`target_id` pair to hold one. The role reading looks like precedent — `ou.role_assigned` targets the OU and carries `role_id` in metadata — but read structurally that precedent says *the possessor is the target and the thing possessed is metadata*, and in a membership the possessor is the person. Granting Alice `manager` does not modify the `manager` role; it modifies what Alice may do. Decisively, `user.created`, `user.updated` and `user.deleted` already target `user`, and between them they carry most authority movement on this platform — the PRIMARY role is changed by `PUT /api/users/{id}`, not through the membership endpoints — so **`target_type=user&target_id=N`, the filter #885 added, now returns one person's complete authority history in a single query**. Targeting the role would have scattered that history across N role ids with nothing able to reassemble it, answering the question for four of six action keys and silently omitting the two that matter most in an incident.
  - **What the rejected alternative would have cost, and why the cost we took is the recoverable one.** Targeting the role would let a role's page answer "who was added and removed here" by `target_id`. We give that up: `role_id` lives in metadata, and #885's filter works on the target, so a role's page answers "who holds it now" from live `memberships` and defers revocation history until metadata is queryable — a JSONB index on PostgreSQL, or a narrow projection table. **That is a missing INDEX over data the trail already holds, and a later query recovers it.** The reverse mistake recovers nothing: an append-only trail keeps the shape every row was written with, so rows pointed at the role could never be re-pointed at the user. Given one irreversible choice, the argument is not which question is more convenient today but which mistake can still be fixed. Writing two rows — one per target — was also rejected: it makes "how many revocations happened" wrong, and incident timelines are built out of exactly those counts.
  - **A revocation row carries what the deleted row held.** `removeMembership()` now reads the row before deleting it — `membership_id`, `role_id`, `ou_id`, `status` and the membership's own `created_at` as `granted_at`, so the trail says not only who took the access away but how long it had been held. The role NAME is captured beside the id, because `memberships.role_id` is `ON DELETE CASCADE`: deleting a role removes every membership holding it with no per-row signal at all, and from that moment a bare id is a pointer into a table that no longer has the row. Grants carry the identical field names, so a grant and its revocation can be matched by `role_id` rather than by judgement.
  - **Ordinary churn is bounded at the source rather than sampled.** No rate limit and no suppression: a trail that drops rows under load drops exactly the rows a bulk attack produces, and its holes are invisible. Volume is bounded instead by the rule **one audited row per administrative act, never one per row touched**. Removing a user from a tenant deletes every membership they hold there and still writes ONE row, enumerating the lost roles in metadata with the authoritative count taken from the DELETE itself, so a capped list is visibly capped rather than quietly short. Creating a user deliberately does NOT emit a second `user.membership.added` beside the already-audited `user.created` — that is the most common membership write in the product, and doubling it is precisely the flood the issue warns about — so `user.created` carries the membership detail instead, including whether it revived an `invited`/`suspended` row, which is a reinstatement and reads very differently in a timeline.
  - **The silent paths are closed, and the remaining silence is deliberate.** Only two of twenty-one membership write paths dispatched anything. Tenant bootstrap (`TenantsApiHandler::provisionInitialAdmin` — the highest-authority grant the platform makes), self-registration's workspace owner, and invitation acceptance now announce their grants post-commit; SSO tenant-trust JIT, SSO first-login provisioning and verified-email domain policy are covered in one place by teaching `MembershipRepository` to announce its own writes, because all three reached the table through it and none held a hook manager — the hole came not from a decision but from three call sites with no reason to think about it, and the next one now inherits the event. Seeders, the scale seeder and migrations stay silent on purpose: they run offline with no request, no actor and no hook manager, so an audit row for them would have to invent the one field the trail exists to record.
  - **`user.updated` now says which role, not merely that a role changed.** It reported `role_changed: true` — a boolean, on the endpoint where most authority on this platform actually moves. That records that authority changed while making it impossible to say what it changed from or to, and "who held admin on the 14th" cannot be reconstructed from a column of booleans. It now carries `previous_role_id`/`role_id` (with names) and the OU and account-status equivalents. A reassignment stays ONE row rather than a synthesised removed+added pair: it is one act, and access is replaced rather than withdrawn.
  - Deliberately deferred: `Events::USER_MEMBERSHIP_ADDED`/`REMOVED` constants for the plugin SDK. The events already exist on the wire and core binds them by string like every other event; publishing constants means an SDK minor bump plus a hand re-vendor of the desktop tree's copy, which is the mechanical change #849 exists to police and does not belong in the same commit as an audit-shape decision.

- **A role is now a PAGE you can link to, not a dialog you scroll twice — `/admin/roles/[id]`, the first record page in the app (part of #882).** Editing a role meant opening `DialogContent max-w-3xl max-h-[90vh] overflow-y-auto`, and inside it a permission picker whose popover is `max-h-80 overflow-y-auto`: **53 core permissions plus every plugin-declared one, in a ~320px window nested inside another scroll region.** A scroll inside a scroll, and no amount of dialog styling fixes a set that size in that space — the operator's words were "editing a role is nightmare with that small modal". The complete set of dynamic segments under `web/app/` was two (`admin/x/[featureId]`, `api/[...path]`) and neither was a record, so "send me the link to that role" was also literally unsatisfiable. This is one hand-built record page that answers both, and it is deliberately a PROTOTYPE: it proves the layout the general, block-DESCRIBED record mechanism should later produce, which is blocked on the three contract gaps in #883.
  - **The page carries what a bigger dialog could not.** A roomier form was the easy half. The half that argues for a page rather than a wider modal is the record's own context: how many people hold this role, who most recently and when, when it was created, whether it is a global base role at all — laid out above the form, because what a role IS on this installation comes before what it may be changed to. The permissions themselves are the acute fix: every resource group (`users:*`, `roles:*`, `ous:*` …) rendered at once in a responsive column grid with a live filter and per-group tri-state select-all, **no height cap and no scroll container of its own anywhere**. That is asserted structurally rather than eyeballed — `role-record-page.test.tsx` queries the grid for `max-h-*`/`overflow-*` and fails if any reappears, because the same defect on a different route is still the defect.
  - **The count needed a backend affordance, and the alternative was a bug we had just finished removing.** There was no per-role headcount anywhere: `AdminApiHandler` computes a `usersPerRole` aggregate for the stats dashboard — every role at once, keyed by NAME — and `GET /api/users` has no role filter, so a client wanting "who has this role" had exactly one option, fetch every user and count. That is wrong at any real tenant size, it walks pages privately (the defect #870 had just removed from the block renderer's fetch hook), and it makes the answer depend on how far the client got before it stopped. So **`GET /api/v1/roles/{id}/assignments`**, ordered by `memberships.created_at` newest-first: `pagination.total` is the headcount and page one IS the recent-assignment history, in one request, with the page capped and the total uncapped. **Gated on the same `admin` role as every other `/api/roles/*` route, deliberately not a new permission** — a new slug ships a grant migration that can only reach the seeded `admin` role, so operators on custom administrative roles lose the capability on upgrade and find out as a 403, which is precisely what #834 documents happening here before.
  - **What that endpoint honestly cannot show, and why it still beat the audit trail.** It reports who HOLDS the role and since when — never a revocation, because removing a membership deletes the row and `user.membership.added`/`user.membership.removed` are dispatched but not audited (`AuditLogger::subscribe()` covers role/user/tenant/ou CRUD and OU role changes only). Auditing those events would have covered revocations, and it was rejected for this PR: the audit target for a membership change is genuinely ambiguous — the OU precedent targets the OU and puts the role in metadata, so the user-membership analogue targets the USER, which a role's page cannot query — and picking wrong bakes a bad shape into a trail that is append-only. Reading live `memberships` is also strictly better for the question actually asked: it is authoritative state, correct for history predating any such change, rather than an event log that would only know about grants since the day it was switched on.
  - **`GET /api/v1/audit-logs` gained `target_id`, and every future record page inherits it.** The filter set was `action`, `actor`, `target_type`, `from`/`to` — narrowable to a KIND of thing but never to one ROW, so "the history of THIS record" was not expressible and a record page would have had to page the tenant's whole trail and sort it out client-side. One bound integer conjunct fixes that for roles, users, OUs, tenants and everything after them. It is added to `GET /api/v1/me/audit-logs` too: the two are documented as analogues differing only in `actor`, and an asymmetry needs a reason. It can only ever NARROW rows the tenant scope already admitted — there is a test that fails if it is ever moved somewhere it could replace the scope — and a non-numeric value is dropped rather than bound, since a string against an integer column is refused outright by PostgreSQL and shrugged off by SQLite, the divergence class that only shows up in CI's Postgres shard.
  - **`GET /api/v1/roles/{id}` now carries `manageable`**, the flag the LIST rows have carried since WC-222. A record page reached by a pasted URL has no list row to read it from, and a page that guesses renders an editable form whose save 404s on a global base role. It is resolved through the same `roleManageableByTenant()` helper the write guards call, not re-derived from a `tenant_id` added to the SELECT: two copies of an authorization rule are two rules, and the second one drifts.
  - **Read-only is a first-class state, not a disabled form.** Two independent gates decide it — the caller's `roles:write` and the role's server-computed `manageable` — and when either says no the page renders the same information with no inputs at all and says which one refused. A read-only page also shows the ROLE'S permissions rather than the installation's whole catalogue, since a viewer reading a ticked-and-unticked catalogue in a form they cannot submit learns the wrong thing.
  - **Additive by construction: the edit modal is still there and still wired.** `RolesScreen` gained an OPTIONAL `onOpenRecord` navigation seam (the package is mounted by Next, a Tauri shell and a Vite harness, none of which share a router). Supplied, the row's Edit action and the row's own name open the record page; omitted, today's modal opens exactly as before. Reverting the whole experiment is deleting one prop at one call site rather than restoring a deleted component — which is the point, since this is a UX bet that has not yet been made in front of users.
  - **RTL was not a pass at the end.** Every inset on the new surfaces is logical (`ps-`/`pe-`/`ms-`/`me-`/`text-start`/`inset-s-`), the back arrow carries `rtl:rotate-180` so it points away from the content in both directions, and no branch of the new code reads the direction — the page mirrors with the app's `<html dir>`. All 52 new strings go through the injected translator into the `admin` domain, declared in file-scoped `@i18n-keys` blocks (these components take a prop-injected translator, so the extractor cannot infer their domain) and extracted with `whity-cli i18n:extract`; permission slugs, group keys and audit action keys render verbatim because they are data and machine identifiers, not source strings.
  - Permission grouping — "the resource segment before the first colon" — existed twice, in the picker and in the read-only panel, and this page would have been the third copy. It is now `permission-groups.ts`, used by all three: three implementations of one rule disagree the first time a slug none of them anticipated shows up, and they disagree in different components on the same screen.
  - **Two smaller things the page surfaced rather than caused.** `Role.createdAt` has been declared since the Path-B extraction while the API has always sent `created_at`; nothing read it — the roles table shows name/description/count — so the type was quietly untrue until "Created" went on screen and rendered an em dash. It is normalized in the adapter, where the wire shape is already translated, rather than by renaming a published column. And the roles table's row-actions trigger was an icon-only button with **no accessible name at all**; it has one now, because the row gained a second button and "the button in this row" stopped being unambiguous for a screen reader.

## [0.2.4] - 2026-08-20

### Added

- **An organizational unit can now say what KIND of thing it is, and a rule written once works on every installation.** `organizational_units` was `(id, tenant_id, parent_id, name, slug, description)` — nothing on the row distinguished a campus from a faculty from a department, so the only thing left to filter on was DEPTH. Depth answers a different question than the one being asked: a single-campus institution has its faculties at depth 0 and a multi-campus one has the equivalent units at depth 1, so "every unit of level 1" returns faculties on one install and departments on the next. It is not stable *within* an install either — inserting a parent above an existing unit renumbers every depth beneath it, silently, with nothing to notify a consumer that it happened. Two separate deployments arrived at the same workaround independently: a parallel unit-id → kind map in their own schema, which drifts the moment a unit is reparented through our API, and drifts invisibly. Migration **102** adds `ou_types(id, tenant_id, type_key, label, sort_order, source, …)` with `UNIQUE(tenant_id, type_key)`, plus a NULLABLE `organizational_units.ou_type_id`. `GET /api/v1/ous?type=faculty` now returns the faculties; `?type=none` returns the units that carry no type.
  - **The key is governed, the vocabulary is not.** These are two different things and they live in two different places on purpose. `type_key` is the stable, code-referenceable identifier a routing rule binds to, governed by the new `Whity\Core\Ou\OuTypeRegistry` exactly as `ResourceTypeRegistry` governs resource types: core types are BARE, a plugin's are PREFIXED from the source the loader supplies (`acme:clinic`), and `core` is a reserved source. The *vocabulary itself* stays tenant data, because one institution's *faculty* is another's *school* and a non-academic tenant has *region → branch → team* with no academic level at all — and a multi-tenant deployment holds both side by side. A core enum cannot express that; `relationship_types` (migration 019) is the existing precedent for a tenant-custom type vocabulary with its own ordering. So the registry governs which keys a **plugin** may contribute, and nothing more.
  - **A plugin cannot mint a bare key, and that is the guarantee.** The prefix comes from `$plugin->getName()`, supplied by the loader, never from anything the plugin returns — so two plugins may each declare `clinic` without colliding, and no install-wide plugin can squat on a name a tenant's own vocabulary might want. Declaring a type does NOT write it into any tenant: a plugin's declaration is a catalogue entry (`GET /api/v1/ou-types/catalog`), and an administrator ADOPTS it explicitly, at which point the declared label and rank become that tenant's starting values and remain overridable. Force-seeding a clinic type into a university's picker would have been a cross-tenant write driven by an install-wide plugin.
  - **Ordering is data.** `sort_order` is what expresses that a campus outranks a faculty outranks a department; ranks are spaced by 10 so a level can be inserted between two existing ones by editing one row. This is also the clearest reason the feature is not modelled on the shipped Taxonomy plugin: a tag group has no rank, and a type is single-valued and structural where a tag is multi-valued and descriptive — nothing in a tag group would stop a unit being both a faculty and a department, and every consumer filtering on it would pay a multi-join through the polymorphic tag tables.
  - **SDK 1.30** (`Whity\Sdk\Ou\PluginOuTypesInterface`). A plugin declares bare slugs and the host namespaces them; `plugins/HelloWorld` implements it as the in-tree reference, so the loader path is exercised by `ci-plugin-smoke` rather than only by unit tests.
  - **Typing is optional, and no new permission was minted.** Existing untyped units keep working unchanged; typing an existing tree is a migration the operator performs against their own data, not one imposed here. The six `/api/v1/ou-types` routes are gated on the existing `ous:read` / `ous:write`, deliberately: a NEW permission ships with a grant migration that can only reach the seeded `admin` role, so every operator running a custom administrative role would silently lose the capability on upgrade and discover it as a 403 — which is exactly what #834 documents happening here already. The `label` is a plain per-tenant string for now; localizing it lands with #821's `localized_texts` rather than growing a second localization mechanism beside it.
- **Two block types every product with an approval step or an audit trail was otherwise going to build for itself: `timeline` and `inbox` (SDK 1.31, part of #868).** The block vocabulary is what stops N products drawing the same screen N different ways, and these two were conspicuously missing from it. `timeline` had no design question worth arguing about — it should have been there already. `inbox` had exactly one, and where its seam falls is the whole of this entry.
  - **`timeline` — an ordered, append-only event list: `actorField`, `actionField`, `timestampField`, plus an optional `noteField` and an optional `fromField`/`toField` pair for a state change.** Data-bound like `dataStat`: one `source` (an owned apiPath, ownership-checked and version-rewritten by the loader exactly as `dataTable.source` is), then per-field mappings. Optional `pageSize` is the same client-side facet `dataTable`/`dataList` carry — it slices rows already fetched and issues no second request. Read-only is a property of the CONTRACT, not a convention: the type declares no endpoint, no verb and no action, so a tree cannot express a writable one and a later prop cannot quietly make it writable without a contract change a reviewer sees.
  - **`inbox` — the items awaiting the current user, each carrying the actions that user may actually take on it.** `source`, `idField`, `titleField`, optional `subtitleField`/`timestampField`/`statusField`/`resourceType`/`pageSize`/`emptyText`, and a required `actions` list (the new `itemActionList` prop-rule kind): `{key, label, method: POST|PUT|PATCH|DELETE, endpoint, scopedPermission?, confirm?, variant?}`. `endpoint` is `{field}`-templated from the item, like a `dataTable` row action.
  - **The seam: the plugin supplies the items, core resolves the permitted actions.** Core has no notion of a task queue, so "items awaiting the current user" can only come from the plugin's own endpoint — `source` is an ordinary owned apiPath and nothing about a queue enters core. What core owns is the other half, and it is the half that justifies the type existing here at all: **which of the declared actions this caller may take on each item.** That is resolved through the new `POST /api/v1/me/permitted-actions`, which answers from the LIVE route table with the same `RoleChecker` calls `RbacMiddleware` makes, in the same order, against the same resolved tenant.
  - **An action does not declare the permission its endpoint is gated on, and that omission is the design.** The route already declares it; the host reads it from there. A slug restated in the block descriptor is a second answer to a question that already has an authoritative one, and it drifts the first time someone re-gates the route and updates one of the two places — with the drift visible only as a 403 after a user clicks. Resolving from the route makes "what the user is shown" and "what the middleware admits" one computation rather than two that agree today. `PermittedActionsApiHandlerTest` asserts that identity directly, by driving the handler and the real `RbacMiddleware` with the same mocked `RoleChecker` over the same router across every (route, held-permission) combination, rather than restating the handler's logic in the test.
  - **`scopedPermission` is the one authorization fact a plugin CAN contribute, because it is the one the route table cannot express.** It is the per-record predicate a plugin's handler applies inside the request — resolved at (`resourceType`, the item's id) through the resource-scoped grants of SDK 1.17/1.22 — and it is evaluated as an ADDITIONAL conjunct: the route gate runs regardless. So it can only ever REMOVE an action from the permitted set, never add one. **That direction is deliberate and load-bearing.** Resource-scoped grants are additive by construction (the scoped answer is a superset of the unscoped one) while the middleware asks the tenant-wide question, so passing a resource scope to the ROUTE gate would answer "allowed" for requests the middleware refuses — a button that 403s. The route gate is therefore resolved unscoped, and a test pins that call shape, because the bug it prevents is invisible in any test whose caller happens to hold the permission tenant-wide anyway. Declaring `scopedPermission` REQUIRES `resourceType`: a per-record check with no record silently becomes the tenant-wide check wearing the wrong name, so the validator refuses it rather than the runtime degrading it.
  - **Fail-closed everywhere it can be.** An action whose path matches no registered route is denied — the request would 404, and a typo'd endpoint becomes a missing button rather than a dead one. While the batch is resolving, and on any resolution failure, the renderer shows NO actions (and says why, on failure). A refused action is ABSENT rather than present-and-disabled: a greyed-out button still advertises work the user cannot do, and a task list of them is noise.
  - **`inbox.actions[].endpoint` is ownership-checked and version-rewritten by the loader**, like a `form`'s `submit` — the method+path must be a write route THIS plugin registered, compared with route params normalized so a declared `{taskId}` matches a registered `{id}`. Unlike `form`/`actionButton` it is deliberately NOT permission-pinned: those pin the route's permission to the block's declared one because the block declares one, and an inbox action declares none. Without the version rewrite every action would resolve to "not permitted" and disappear — fail-closed, but silently, which is why there is a test for it.
  - **The rejected alternative — have the plugin's queue endpoint return the permitted actions per item — is less code in core and is exactly the failure the block vocabulary exists to prevent.** Every product would re-derive authorization beside the host's: membership gating, OU-ancestor inheritance, role hierarchy, live delegations, catalogue validation. Each copy drifts from the middleware in its own direction, and the drift surfaces as a 403 after a click rather than as a failing test.
  - **Both renderers ship together and are pinned against divergence.** The desktop template's `plugin-blocks/block-renderer.tsx` is a hand-written twin of the web one that has silently diverged twice (#826's unrendered sort/filter/pageSize props, #847's form payloads), so `web/__tests__/block-renderer-workflow.test.tsx` and `templates/tauri-desktop/src/plugin-blocks/__tests__/block-renderer-workflow.test.tsx` assert the SAME contract — identical permitted-actions batch shape, identical `ref` scheme (`"<itemId> <actionKey>"`), identical fail-closed behaviour — under the one Jest project that already scans both trees (#850). The offline host gets its own `POST /__whity/permitted-actions`, answering from ITS route table through the same `PermissionResolver` its dispatch gate uses, so an inbox renders the same permitted set on a device as on the server.
  - **The fetch side is #867's, not a second mechanism of their own.** Both types consume `usePluginData` UNCHANGED, so they inherited #870's pagination fix the moment it landed — a queue or a history longer than its endpoint's first page now loads in full, and an incomplete load says so rather than rendering a truncated set as the whole thing. `pageSize` here is only the client-side slice over what that hook returned. Adding a private page walk to either block would have been the same defect in a second place, and the place nobody would think to look for it.
  - **Assumption flagged for the requesting team, still unconfirmed:** they were asked whether they expected core to own the task queue itself and had not answered when this landed. The shape built is the decided one — plugin supplies the items, core resolves the actions. Core owning a queue is a much larger change and a different issue.
  - `UiKitShowcase` gains a **Workflow** tab with a live instance of each (the every-type coverage gate), plus three demo endpoints — `GET /api/uikit/demo/events`, `GET /api/uikit/demo/tasks`, and the two `POST /api/uikit/demo/tasks/{id}/…` action routes whose own `requiredPermission` the host resolves per caller. The showcase declaration is worth reading as the documentation for the type: note what it does not contain.

- **A plugin can now ask for a SCOPE over the organizational-unit tree — "every department under this faculty" — and store it as a rule that is still correct after somebody reparents a unit (`ouScopePicker`, SDK 1.32, closing #868).** The third and last block type in #868, held back until #822 gave units a type and #870 stopped data-bound blocks rendering page one as the whole collection. What existed before was a flat unit dropdown and nothing else: `referenceSelect` pointed at a unit collection submits ONE id, so the only way to express "the departments under Engineering" was to expand it in the UI and persist the ids it happened to contain that day. That list is wrong the first time a department is added, removed or moved, it is wrong silently, and it is the same parallel unit-id map two deployments independently built in their own schemas — the one #822 exists to delete. A rule is not a list of ids that happen to match; it is the question, kept, and re-asked at execution time.
  - **The value shape is `{unit, scope, type}`, and `scope` is always written.** `unit` is the anchor unit's id or `null` for the whole tenant; `scope` is one of `unit` / `subtree` / `children`; `type` is an OU type key (#822) or `null` for any kind. The single decision worth arguing about is that `scope` is a required, explicit discriminator rather than something inferred from which other fields are set. **"This unit" and "this unit and everything below it" are different answers, and nothing else in the object tells them apart** — a shape where the presence of a `type` implied a subtree would make a consumer guess, and it would guess differently in each product. The resolution is a closed table a consumer switches on:

    | `unit` | `scope`    | resolves to                                  |
    |--------|------------|----------------------------------------------|
    | id     | `unit`     | exactly that unit                            |
    | id     | `children` | its direct children (`?parent_id=<id>`)      |
    | id     | `subtree`  | it **and** every descendant (inclusive)      |
    | `null` | `children` | the root units (`?parent_id=0`)              |
    | `null` | `subtree`  | every unit in the tenant                     |
    | `null` | `unit`     | never produced — the nothing-selected state  |

    `type`, when non-null, narrows whatever that produced (`?type=<key>`), applied AFTER the scope expands and never instead of it. `subtree` is inclusive of the anchor, matching `getDescendantIds()` and `TwoFactorPoliciesApiHandler::descendantOuIds()`, the two descendant walks core already has.
  - **The block declares NO `source`, and that is structural rather than a convenience.** Every other fetching leaf names an apiPath the loader ownership-checks against the routes the DECLARING plugin registered, so `/api/v1/ous` is unnameable from a block tree: a `referenceSelect` aimed there does not fetch the org chart, it drops the entire feature. The only way to satisfy that gate is for the plugin to republish core's hierarchy through a route of its own — which is precisely the drift being removed. So the host renderer reads the units and the type vocabulary from core's own `GET /api/v1/ous` and `GET /api/v1/ou-types`, under the caller's own session and the `ous:read` gate those routes already carry. Two things follow, both wanted: a caller who may not read the org chart cannot build a rule over it, and a plugin has no prop with which to point the control anywhere else. `UiKitShowcasePluginTest` asserts the absence of a `source` prop rather than assuming it, because adding one later would silently move the hierarchy back behind a plugin route.
  - **`anchorType` and the value's `type` are deliberately two props, not one.** They answer different questions at different times: `anchorType` restricts which units may ANCHOR the rule and is applied as `?type=` on the picker's own unit fetch (design time, by the plugin author); the value's `type` restricts the set the scope RESOLVES to (choose time, by the user, or pinned by the author with `memberType`). "Every department under a faculty" needs both, and collapsing them into one prop would make that rule unexpressible. Filtering the anchor list server-side rather than in the browser also matters at size: a tenant with ten thousand units should not ship all of them to discard nine thousand.
  - **Two combinations the contract says cannot exist are unreachable rather than merely discouraged.** A `unit` scope carries no kind filter — a filter over the single unit the user just picked by hand can only ever subtract it — so the kind control disappears and the rule is written with `type: null`; and dropping the anchor while the scope is `unit` moves the scope rather than leaving `{unit: null, scope: 'unit'}`, the one row of the table that resolves to nothing. `BlockValidator` refuses `memberType` beside a `scopes` list of exactly `['unit']` at load time, the same cross-prop treatment `inbox.scopedPermission` gets: an author who wrote it meant something, and it is not what the declaration does.
  - **An untouched picker submits nothing at all.** Neither renderer seeds a value for it, so a form that EDITS a stored rule cannot blank it by being opened and saved — the failure #847 shipped against the sync endpoints' full-row replaces. Once touched, every control writes the WHOLE rule composed from the current one, never a partial patch, so there is no code path that can persist a rule missing its `scope`. Both renderer suites assert exactly that, on the payload rather than the pixels.
  - **The rejected alternative was to persist the resolved unit ids and re-resolve on a schedule.** It needs no new block type, no new value shape, and no consumer changes — the stored value stays a list of ids every product already knows how to read. It also reintroduces the entire defect: between resolutions the list is wrong, nothing surfaces that it is wrong, and the window is however long the schedule is. Worse, it makes the drift a background job's problem rather than a data-modelling one, so the first symptom is a permission or a routing rule quietly applying to the wrong set of units — which is how the parallel unit-id maps failed in the first place.
  - **Both renderers ship together and are pinned against divergence.** `web/__tests__/block-renderer-ou-scope.test.tsx` and `templates/tauri-desktop/src/plugin-blocks/__tests__/block-renderer-ou-scope.test.tsx` assert the SAME 18 contract points under the one Jest project that scans both trees (#850). The desktop twin issues the same two requests through its `php_request` proxy; today's offline host serves no OU routes, so it answers 404 and the control reports that it could not load them, with a retry — the same code path taking the branch its environment produces, rather than a hard-coded "not available here" that would rot the day a host does serve them. The picker consumes `usePluginData` unchanged and therefore inherits #870's pagination walk: a unit list longer than one page loads in full, and a walk that could not finish says so instead of offering a truncated tree. That was the blocking dependency — filtering a truncated list is not filtering, and a picker missing unit 26 reads as "the department was never created".
  - `UiKitShowcase` gains a live instance in the interactive form (the every-type coverage gate) plus a documentation card carrying the value shape, the resolution table, and the eight lines a consumer writes to resolve a stored rule. It declares no new endpoint: there is nothing plugin-side for this block to fetch.

### Documentation

- **The `blocks` screen type is documented on the interface a plugin author actually reads.** `PluginFrontendInterface`'s docblock listed `crud`, `action`, `custom` and `embed` and never mentioned `blocks` — despite it being first-class since SDK 1.6: validated in the loader beside the other four, present in the OpenAPI enum, and carrying its own fail-closed block-tree validation. The contract was recorded in `Sdk.php`'s version ledger, which is not where someone writing a frontend feature looks. A downstream team reported this from the position it puts them in: they ship three `blocks` screens that work, and asked whether the type was unstable and they should move to `embed`. It is stable; only the documentation lagged.
  - **Two properties are documented that a plugin author could not previously discover and would otherwise find by debugging.** Block-tree validation runs at SERVE time, not load time — a malformed tree does not fail discovery, the feature is omitted from `/api/frontend-features` and the errors go to the host's log, so the symptom is a screen that silently does not appear for anyone and the diagnosis is somewhere they may not think to look. And the validation is ADDITIONAL to the per-caller permission filter, never a substitute for it.
  - **The entry says when to prefer `blocks` over its neighbours**, since that is the question the omission left unanswered: `blocks` and `embed` both need zero host-application edits, but a block tree is DESCRIBED rather than framed — so it inherits the host's theme, RTL handling and every renderer improvement, and the same declaration also renders on the desktop offline host.
### Fixed

- **Two faculties can each have a Computer Science department.** `organizational_units` carried `UNIQUE(tenant_id, name)` from migration 005, which is the right rule for a flat list and the wrong rule for a tree: campus → faculty → department is the normal shape of the thing being modelled, and in that shape two campuses each have an *Engineering* faculty and two faculties each have a *Computer Science* department. A deployment does not hit this while its tree is small; it hits it the first time the tree is realistic, and the 409 it gets describes no real conflict. Migration **103** scopes the rule to SIBLINGS.
  - **It could not be done with `UNIQUE(tenant_id, parent_id, name)`.** That constraint would not do what it says: PostgreSQL treats NULLs as DISTINCT, so every root unit (`parent_id IS NULL`) falls outside it entirely and a tenant could end up with two roots both called *Main Campus*. Tightening the bottom of the tree would have loosened the top — worse than leaving it alone, and silent about it. The rule is therefore a PAIR of partial unique indexes, the treatment migration 094 gave `memberships`: `UNIQUE (tenant_id, parent_id, name) WHERE parent_id IS NOT NULL` and `UNIQUE (tenant_id, name) WHERE parent_id IS NULL`, with the roots as one sibling set. A single `UNIQUE (tenant_id, COALESCE(parent_id, 0), name)` expression index was rejected: it is correct only while no unit can have id 0, and that invariant lives nowhere but a comment.
  - **`UNIQUE(tenant_id, slug)` was deliberately left alone.** A slug is URL identity — scoping it to siblings means `/ous/computer-science` no longer resolves to one unit without the full ancestor path, so every stored link and every admin route would have to carry the path instead. Keeping the wider rule means the second sibling-legal *Computer Science* cannot take `computer-science`, so the API disambiguates the slug (`computer-science-2`) rather than refusing the unit. Refusing it would have made relaxing the name rule pointless: the 409 would simply have moved from the name check to the slug check. A name that reduces to nothing under the slug generator — an Arabic-only name, which is a first-class requirement here — now falls back to a stem rather than producing an empty slug that collides with the next such name.
  - A pure re-parent is checked against the TARGET sibling set, not only renames: moving a unit under a parent that already holds its name is a 409 rather than a partial-index violation surfacing as a 500. The old rule was strictly stronger than the new one, so every existing row already satisfies both indexes and no data migration is needed; `down()` refuses (naming the collisions) rather than choosing which unit loses its name.

- **Every data-bound plugin block rendered page one of its source and presented it as the whole collection.** `usePluginData` — the fetch hook behind `dataTable`, `dataList`, `dataStat`, `chart`, `selector`, `referenceSelect` and every `select` drawing options from a source, in **both** the web and desktop renderers — issued exactly one request for the block's `source` and handed `body.data` straight to the block. Every core list endpoint is paginated at `PaginationParams::DEFAULT_PER_PAGE = 25`, so a block pointed at one showed the first 25 rows with no error, no warning, and nothing in the rendered output to suggest the list was short. This is precisely the defect #823/#824 removed from core's own OU tree and pickers, reproduced in the generic component every plugin uses for the same job: on the 48-unit reporting instance it arrived as **"the department was never created"**, because an operator who cannot find a row concludes the row does not exist rather than that the list was truncated. It was found while triaging an OU picker block rather than reported by anyone, which is the point — a plugin author re-inherits this invisibly, and it only manifests past whatever page size the endpoint happens to use. It also silently defeats work already scheduled on top of it: filtering a truncated list is not filtering.
  - **Detection keys off the platform's own `pagination` envelope, and the first request is still the block's `source` verbatim.** The hook fetches what the block declared, exactly as it always has, and only then looks at what came back: a `pagination` block carrying numeric `total`/`totalPages` — tested by the same predicate `walkPages()` itself uses, now exported, so the two can never disagree about what "paginated" means — and a `data` array shorter than that `total`. A plugin's own unpaginated route, a `dataStat`'s single object, and a paginated endpoint whose whole set fit in the first page therefore behave exactly as before, down to the URL requested and the number of requests issued. That was the regression risk that mattered most, since most block sources are a plugin's own small route. The rejected alternative — appending `?page=1&per_page=100` to every source unconditionally — is simpler and needs no probe, but it rewrites the request for every plugin route on the platform on the chance that it might be paginated, and a route that reads `per_page` as something of its own returns different data for a reason its author cannot see from the block DSL. Once a walk is warranted it restarts from page 1 at the server maximum rather than continuing from page 2 at the default: one wasted request, in exchange for `fetchAllPages()` being reused exactly as written and roughly four times fewer round trips for any source large enough to reach that branch.
  - **A block that could not load every page says so; it never renders what it managed to get.** An incomplete walk maps to the hook's existing `error` state, so the block draws the error panel and retry every consumer already renders, and `parse` is never called with a partial list — not for a frame. That covers both directions: a page request that fails mid-walk, and the walk reaching `fetchAllPages()`'s 100-request cap against an accidentally-huge endpoint or a `totalPages` that never terminates. Hitting the bound is a failure, not a quiet stop with what it had. The rejected alternative was a fifth `incomplete` status carrying the rows that did arrive plus the size of the gap, the way #824's three OU pickers each state theirs — richer, and it would let a block say "showing 100 of 240" instead of nothing. It is also a breaking change to a hook consumed by every data-bound renderer in both hosts, each of which would have to be taught not to render the short list, and a consumer that got it wrong would produce exactly the partial render that was the whole finding of #824. The state that *cannot* be rendered partially is the safe default; a per-block message can be added when a block exists that wants one.
  - **The hang guard is now re-armed per request rather than spent on the whole load.** It exists to bound one unanswered request, and a paginated source legitimately costs several round trips — leaving it as a 15-second budget for the entire walk would have manufactured the "could not load everything" error this change exists to make rare.
  - **The desktop renderer had the same defect and gets the same rules, from a second copy of the walk rather than a shared import.** `templates/tauri-desktop/src/plugin-blocks/use-plugin-data.ts` is a hand-written twin of web's and fetched one page for the same reason. It cannot import `web/lib/api/fetch-all-pages.ts`: the template ships to consumers who take `@amroksaleh/*` from the registry and have no `web/` at all. Hoisting the helper into `@amroksaleh/features` would let one implementation serve both — the honest fix — at the cost of moving a file four core screens already depend on, adding a fetch utility to a package that documents itself as data-source-agnostic feature *UI*, and pinning the template to a newer package version; that is a packaging change and deserves its own. The termination and completeness rules are copied verbatim, and #847's cross-renderer parity test grew its other half — same block tree ⇒ same **requests**, not just the same submitted payload — with the expected walk pinned literally, so a shared regression back to one request fails the test rather than passing it as agreement.

- **A refused cross-tenant role grant is now an audit record instead of a line on STDERR — which is also why the scheduled mutation-testing job had not actually run since 9 August.** `ResourceRoleAssignmentRepository` reported a grant it correctly refused with a bare `error_log()`. In the CLI SAPI that writes to STDERR, and a refusal is an EXPECTED, handled outcome the test suite trips deliberately — so a fully PASSING suite emitted on STDERR. Infection stops its initial test run on the first byte of STDERR it observes (`InitialTestsRunner`: `if ($type === Process::ERR) { $process->stop(); }`), so the job died ~159 tests into 433 with SIGTERM and reported *"Project tests must be in a passing state before running Infection. Infection runs the test suite in a RANDOM order. Make sure your tests do not have hidden dependencies."* — boilerplate describing a bug the repository did not have. Nothing was order-dependent; the suite was speaking on the wrong file descriptor. The refusal now goes to an injected PSR-3 sink defaulting to `NullLogger`, the contract `EnforceTenantIsolation` already uses: `public/index.php` passes the application logger, so operators still get the record (now as a structured `[warning] RBAC: resource role grant denied — role not visible to tenant {"tenant_id":…,"role_id":…}` line rather than `[rbac] denied resource role grant: tenant_id=… role_id=…`), while a test that trips the guard on purpose stays silent.
  - **The failure was invisible for eleven days because a skipped job leaves the RUN green.** The workflow's `changes` gate skips the mutation job when `main` has not moved in the window, and GitHub reports a run whose only real job was skipped as *success*. Between 18 and 20 August `main` sat still, so eight consecutive "successful" runs never executed a single test — and the last run that genuinely executed had failed. Every scheduled run that actually ran since 5bc5c2f1 (#722, which introduced the `error_log`) had failed the same way.

## [0.2.3] - 2026-08-18

### Added

- **Offline-first, two-way sync is now a contract a plugin declares, not a protocol a plugin re-implements.** `Whity\Sdk\Sync\SyncController` drives the entire sync lifecycle against any table described by the new `Whity\Sdk\Sync\SyncableResource` descriptor. Until now exactly one table on the planet spoke the wire contract the desktop sync engine expects — `demo_catalog_items` — and it did so through ~500 lines of bespoke tenant-scoped CRUD/sync SQL inside `DemoCatalogApiHandler`. Any second feature that wanted to work offline had to copy that file and get every one of its edge cases right again: the idempotency key, the conflict status, the tombstone semantics, the cursor arithmetic, the tenant predicate on every statement. A copy that got one of them subtly wrong would not fail loudly — it would sync, and lose a row. `DemoCatalog` is now the engine's **first consumer** rather than its only implementation (behaviour preserved, proven by its existing items + sync real-engine suites), and `Relations` is the second. This is the rail the whole desktop/offline story runs on, so it is worth reading as documentation: a plugin author who implements the five-method descriptor gets all of the following and writes none of it.
  - **What a table must carry to be syncable, exactly.** `version`, `client_uuid`, `deleted_at`, `updated_by`, `change_seq`, `created_at`, `updated_at` (the controller's `SYNC_COLUMNS`), plus a **UNIQUE index on `(tenant_id, client_uuid)`** — the idempotent create is an `ON CONFLICT (tenant_id, client_uuid) DO NOTHING`, so without that index the guarantee silently degrades into duplicate rows on every retried offline create. The descriptor itself declares only `table()`, `sequenceKey()`, `domainColumns()`, `validate()` and `toPublicFields()`: the resource describes *its own* fields, and the controller wraps every sync field around them, so the wire shape cannot drift resource by resource.
  - **Create is idempotent on `clientUuid`, and answers `201` or `200` rather than `409`.** A device that wrote offline and lost its connection mid-POST cannot know whether the row landed; making the retry an error would force every client to hand-roll a read-before-write that races anyway. A genuine create is `201`, a retry returns the row that already exists with `200`, and the caller distinguishes them by the status alone. A `clientUuid` the caller does not supply is generated server-side, so the column is never null and the index never useless.
  - **Update and delete are optimistic-concurrency guarded, and a conflict answers with the server's row.** `If-Match: <version>` (or a body `baseVersion`) is folded into the `WHERE`, so a stale edit updates zero rows and comes back `409` carrying **`serverItem`** — the current row, in the same public shape. Returning it in the conflict body is the design decision: a bare `409` sends a disconnected client back for a second round trip it may not be able to make, which is precisely the situation it is in.
  - **Delete is a tombstone, never a row removal, and is idempotent.** `deleted_at` is stamped and `change_seq` re-issued, so the deletion propagates through the changes feed like any other write — a hard `DELETE` is invisible to every device that has not yet pulled, which is how a deleted record resurrects itself on the next push. Deleting an already-tombstoned row is `200` with that tombstone, not `404`, because a retried delete is the normal case offline.
  - **The changes feed is `change_seq`-ordered, not timestamp-ordered.** `?updatedSince=<cursor>` returns rows with `change_seq > cursor` ascending, tombstones included by default, with `{data, cursor, hasMore}` and a `limit` capped at 500 (default 100; `hasMore` is derived by fetching one extra row). Every write stamps a fresh platform-wide sequence value from the host `SequenceAllocator`, so the ordering is unique and monotonic and cannot collapse two writes into the same instant the way a `updated_at` cursor does — a clock-based cursor either re-delivers a whole second of rows forever or skips one. Gaps in the sequence are harmless by construction because the predicate is strictly `>`.
  - **Tenant scoping is enforced once, in the engine, not once per plugin.** Every non-system statement carries an explicit `tenant_id` predicate; the system tenant (id 0) is the documented unscoped read context and **can never own a created row** (`POST` from tenant 0 is a `403`), so the sees-all exception cannot become a way to write records nobody owns. The tenant id is passed *in* by the handler from the host's `TenantContext` — the SDK never reaches into core, which is what lets the identical controller run inside the desktop's offline PHP host where there is no `TenantContext` at all.
  - **Table and column names are trusted, code-defined identifiers, validated before interpolation.** SQL has no parameterised identifier syntax, so the controller validates `table()` and every `domainColumns()` entry against `^[a-z_][a-z0-9_]*$` **at construction** and throws otherwise; every value is bound. A descriptor built from request data would fail loudly at construction rather than compose a query.
  - **`update` is a FULL ROW REPLACE, and this is the one thing that surprises a REST-shaped caller.** The sync model is "a client pushes its whole local copy", so `validate($body, requireAll: true)` runs on updates too and any domain column absent from the body is written **null** — a `PATCH` that sends one field silently clears the others. That is correct for a sync client (it always holds the full row) and is called out here because it differs from core's own partial-merge `PATCH` on the same resources.
  - **Available from SDK 1.27**, which is the constraint `RelationsPlugin` declares (`^1.27`). The `Whity\Sdk\Sdk` version ledger does not name the `Sync` namespace among its minors — it landed inside 1.27 without its own entry — so `^1.27` is the constraint to write; there is no narrower one that means "I need the sync engine".
- **A desktop device can fetch its plugins from the same server it authenticates against.** `GET /api/v1/desktop-plugins` (the catalog, grouped by plugin, newest version first) and `GET /api/v1/desktop-plugins/{name}/versions/{version}/download` (the raw zip), backed by `desktop_plugin_releases` (migration **097**) and gated by the new **`desktop-plugins:read`** permission (migration **098** upserts it and grants it to the built-in `admin` role). There is no new auth mechanism and no store/allowlist concept: a device presents the same bearer access token `POST /api/v1/devices/token` already issues for sync, and the backend it is pointed at *is* the plugin source. The alternative — reusing the plugin-store install path — would have meant a desktop device negotiating an SSRF allowlist to reach its own server.
  - **A separate permission from `plugins:read`, deliberately.** `plugins:read` shows an operator the server's own installed-plugin list; `desktop-plugins:read` hands a device proprietary, obfuscated builds. Collapsing them would make every operator who can view the plugins page also able to download every packaged product.
  - **Operator consequence, stated plainly: the catalog is GLOBAL in v1.** `desktop_plugin_releases` carries no `tenant_id`, `catalog()` applies no filter, and the release pipeline writes no scoping column — so *every* authenticated device on the instance holding `desktop-plugins:read` sees and can download *every* release, regardless of tenant. This matches the migration, the handler and the shipped client, and per-tenant entitlement is a deferred follow-up that requires a scoping column **and** a matching filter in `catalog()`. On a multi-tenant install this is the fact to know before cataloguing a customer-specific plugin.
  - **`{name}` is case-sensitive and mixed-case on purpose** (`^[A-Za-z0-9_-]{1,128}$`, published as `DesktopPluginsApiHandler::NAME_PATTERN`), bounded to the `plugin_name VARCHAR(128)` column. The name becomes the plugin's top-level directory on the device, and the device's PSR-4 loader maps that directory name to the namespace root — so `DemoCatalog` must stay `DemoCatalog`. The release pipeline validates against this same constant, which makes "a name that cannot be downloaded can never be catalogued" a property rather than a convention.
  - **A missing release is a generic `404`**, never "that plugin exists but not that version" — the response must not become a way to enumerate which products an instance carries.
  - **Releases are immutable and stored outside the web root.** `(plugin_name, version)` is unique; `storage_path` is relative to the handler's configured storage directory (`storage/desktop-plugins`), so the bytes are only ever reachable through the permission-gated route. `desktop_plugin_releases` is registered in `CoreTables` against its migration — an unregistered core table is one a plugin could claim ownership of and declare a referential guard over.
  - Both routes ship in `RouteCatalogueCompletenessTest::KNOWN_UNDOCUMENTED`: they are consumed by the desktop app rather than the web UI, and full OpenAPI components follow in a dedicated documentation task.
- **The producing half of that catalog: a source-obfuscating release pipeline, `bin/desktop-plugin-release`.** Migration 097 and the handler only *serve* what is already catalogued; nothing built a package. `Whity\Core\DesktopPlugins\DesktopPluginReleaseService` now does obfuscate → package → store → catalogue in one command, and `docs/wiki/Desktop-Plugin-Releases.md` documents the whole contract.
  - **Obfuscation is source-level ONLY, and that is forced by the device, not a compromise.** The desktop ships an unmodified FrankenPHP and loads a downloaded plugin the same way it loads a bundled one: every `.php` file under the directory is eager-required and classes resolve **by file path** from the top-level directory name. So class, interface, trait, enum, namespace, method, property, constant and function names — and the files they live in — must survive byte-for-byte. A conventional class/method-renaming obfuscator run with its defaults produces a package the device silently *quarantines*. What `PluginObfuscator` does instead: strip every comment and docblock (always), rename local variables inside provably clean scopes (default on), and optionally re-encode string literals as `\base64_decode(…)` (`--encode-strings`, off by default). Re-printing from the AST also normalises the original formatting.
  - **"Provably clean" is defined narrowly and fails closed.** `LocalVariableRenamer` renames a scope's locals only when the scope contains no nested closure or arrow function (one rule that sidesteps every capture question), uses no name-reflective construct (`compact`/`extract`/`get_defined_vars`/`func_get_args`/`parse_str`/`eval`/variable-variables/`global`) — including through indirection, since `call_user_func('extract', …)` runs in the calling scope — and even then never touches parameters (PHP 8 named arguments), `use (...)` captures, `$this` or superglobals. Coverage is traded for correctness deliberately: a method containing a closure keeps its own variable names, while that closure's locals are still renamed if it is itself clean.
  - **The output is re-parsed before it is emitted.** A transform that would produce un-parseable PHP aborts the build with `ObfuscationException` rather than shipping a package that fails on the device, where the only symptom is a quarantined plugin.
  - **A bytecode encoder was rejected.** ionCube/SourceGuardian would mean bundling a proprietary loader extension into every platform's FrankenPHP build. This is obfuscation — raise the cost of reading and modifying — and is documented as such rather than sold as encryption.
  - **The package contract the device enforces is mirrored on the producing side, using the same constants.** Exactly one top-level directory whose name equals the plugin name; ≤ 32 MiB total, ≤ 2000 entries, ≤ 16 MiB per uncompressed entry, ≤ 64 MiB uncompressed, compression ratio ≤ 200:1 — read from `Whity\Core\PluginInstaller`'s own public constants (and its `exceedsCompressionRatio()`) so the packager and the installer cannot drift apart into a package that builds and will not install.
  - **The checksum is computed once, from the final zip on disk, and re-verified after the move**, so the `sha256` a device checks can never describe a pre-image rather than the served bytes. The package is placed on disk *before* the row is inserted (a catalogued release always has its bytes), and a failed insert removes the file again. `(plugin_name, version)` is immutable; `--force` re-cuts a botched build with an `ON CONFLICT DO UPDATE` that **preserves the row's id and `created_at`**, so nothing downstream keyed on a release id is invalidated by a re-cut.
  - **The pipeline depends on `nikic/php-parser`, a dev dependency — it cannot run from the production `--no-dev` image.** Releases are cut in CI or a dev environment, never on the box serving traffic. That is a deployment fact worth knowing before reaching for the command on a server.
- **Plugin installation on a desktop device is now mandatory and automatic — the server's catalog is the single source of truth for what a device runs.** Every successful login reconciles the device's installed plugin set to *exactly* match the catalog: install what is missing, update what is stale, remove what the catalog no longer lists (a revoked entitlement). There is no manual install or uninstall control left anywhere in the desktop UI; `plugin_sync_status` is a read-only snapshot of the last pass. An opt-in install list would have meant a device's capabilities were whatever its user last clicked, which is not a thing an operator can reason about or revoke.
  - **A failed plugin sync never fails the login.** It runs fire-and-forget on a background thread (a multi-plugin sync plus a FrankenPHP restart exceeds the awaited command's budget) and reports through the `plugin-sync:status` event and a persisted `plugin_sync_state` row. A catalog endpoint that is down must not lock a user out of an app they already have installed.
  - **Per-plugin failures are collected, not fatal.** Only a catalog *fetch* failure aborts the pass — without it there is nothing to converge against. One plugin that fails to install must not strand the rest of the device's set on stale versions.
  - **Not wired into the 45-second background sync heartbeat.** That heartbeat is a connectivity probe; reconciling on it would mean a catalog fetch, and possibly a FrankenPHP restart, every 45 seconds even when nothing on the server changed. FrankenPHP is restarted only when something actually landed on disk.
  - **A missing or corrupt `.whity-version` marker forces a re-install** rather than being trusted or ignored — self-healing back to a known-good state beats leaving an install whose version nobody can verify.
  - **Two plugin roots, bundled first.** The device scans the read-only bundled root shipped with the installer and then the writable server-synced root, registering namespaces and gating every candidate across both in one pass, so a downloaded plugin can never shadow a bundled one and a cross-root name collision is quarantined rather than resolved by luck.
  - **A downloaded plugin lands ENABLED, not disabled-pending-approval.** There is no admin-approval workflow on a single-user desktop, and the PHP-side requirements gate already quarantines a broken or incompatible plugin without crashing boot — the same safety a "disabled" landing would buy, without a second step nobody is there to take.
- **The desktop app can update itself, and the server decides when.** `GET /api/v1/desktop-app-updates/latest?target=…&current_version=…` implements Tauri's dynamic-update-check protocol against the new `desktop_app_releases` table (migration **099**), gated on the new **`desktop-app-updates:read`** permission (migration **100**), with `bin/desktop-app-release` to register a build and `.github/workflows/tauri-desktop-release.yml` to produce one. See [`docs/wiki/Desktop-App-Updates.md`](docs/wiki/Desktop-App-Updates.md).
  - **The server answers the version question, not the client**, returning `204 No Content` when the caller is current, ahead, on an unrecognised target, or sent a malformed request — **fail closed: an unparseable request can never resolve to "yes, update"** — and otherwise the exact `{version, notes, pub_date, url, signature}` shape `tauri-plugin-updater` expects. A client-side comparison would put the rollout decision on the machine being rolled out to.
  - **The self-update check runs strictly BEFORE plugin sync, on every login.** A plugin package assumes a compatible app runtime. When an update is found the process installs it and relaunches, which is what skips that login's plugin sync — the relaunched binary syncs on its own next login. Handing a new plugin package to an old runtime is the failure this ordering exists to prevent.
  - **The updater endpoint and bearer token are set at the runtime call site, not in `tauri.conf.json`.** The backend URL is per-build configurable and the access token is short-lived and re-exchanged, so neither can be baked in. What *does* stay static in `tauri.conf.json` is the minisign **public** key — that one genuinely is a build-time trust anchor.
  - **Signing is a human-custodied prerequisite CI cannot create for itself.** The minisign keypair is generated by a person (`npx tauri signer generate`); the private key becomes a write-only GitHub Actions secret and must also live in a real vault, because **losing it means no future release can ever be accepted as an update by any copy already signed under it**.
  - **CI builds, signs and publishes — it does not register the release against anyone's database.** The product is self-hosted per instance, so CI cannot reach into a customer's `desktop_app_releases`; an operator runs `bin/desktop-app-release` against their own deployment (`--db-dsn`, or the app's `DB_*` environment) once the artifact is published. The same posture as the desktop-plugin pipeline. Windows-only in v1, the only platform verified end to end. The desktop app's version is its own axis and is not `CoreVersion::VERSION` — its releases are tagged `tauri-desktop-vX.Y.Z`.
  - `desktop_app_releases` is global in v1, matching `desktop_plugin_releases`; `(version, target)` is unique and the table stores only where the installer lives and how to verify it, never the binary. Registered in `CoreTables`, and the route is in `KNOWN_UNDOCUMENTED` pending its documentation task.

On the desktop's offline host, where core's routes do not exist, the plugin's are the only ones. The collision is the safety mechanism that makes "both exist at once" survivable until the cutover slice removes core Relations.

  - **Updates through this plugin are full-row replaces**, per the sync engine above, unlike core's partial-merge `PATCH` on the same resource. Correct for the desktop client, which always holds the whole row — and recorded here because at cutover the web caller must send full rows or a partial-merge path must be added.

- **The desktop's offline host now serves its own frontend-feature list, so a plugin's block UI renders on a device with no per-plugin TypeScript.** `GET /__whity/frontend-features` (offline-host-local — it touches neither `src/` nor `sdk/`) is the counterpart to production's `GET /api/v1/frontend/features`, and the desktop's generic renderer maps every block type in the SDK's `BlockContract` onto the shared UI primitives, fetching and submitting through the existing PHP-host proxy. An installed plugin's declared features are merged into the sidebar and a generic `/plugins/x/:id` route — a new plugin's screen appears with zero desktop-side code.
  - **Deliberately narrower than production's handler, and the difference is a security judgement.** Production polices cross-plugin permission *ownership* (a `requiredPermission` must be declared by the same plugin; the first plugin to claim a path owns it) because it hosts plugins of mixed provenance. A device runs a single, server-entitled plugin set that the release pipeline already vetted, so that policing does not pay for itself there. - **Plugin block UI can now open something in place: `modal` and `drawer` container types, implemented by the web renderer and the desktop renderer as one contract.** Every block a plugin declared rendered flat on a single page, so the only way to offer "edit this row" was a `href` row action navigating to a second screen the plugin also had to declare — losing the list's page, filter and scroll position on the way there and again on the way back, and doubling the tree for what is one interaction. `modal` (→ `Dialog`) and `drawer` (→ `Sheet`) are containers holding one `children` slot, typically a `form`, opened either by their own optional `trigger` (a plain string label, deliberately not a nested block — a trigger slot would let a plugin put a `dataTable` inside a button) or, when `trigger` is omitted, only programmatically by a row action. It landed as a matched pair on purpose: the SDK contract plus the web `BlockRenderer` (#827) and the desktop renderer (#826), so a `screen: 'blocks'` tree is never a thing one host renders and the other silently drops.
  - **`dataTable.rowActions` gains a third kind, `open: <targetBlockId>`**, joining `href` and `endpoint`+`method` under the same exactly-one rule — an entry carrying two of the three is now a validation error naming all three. Clicking it publishes the whole clicked row into the master-detail context under the target overlay's id and opens it. That indirection is what makes "edit *this* row" expressible at all: the overlay is declared once, elsewhere in the tree, and every row reuses it. Declaring one overlay per row — the only alternative without a context — would have made the size of the block tree a function of the data it displays.
  - **The overlay reads the published row through `defaultFrom`, a SIBLING of `default` and never an overload of it.** Each scalar input gains `defaultFrom`, and `params.from` on a data-bound block accepts the same addressing: a dotted `{targetId}.{field}` reading the published row, or a bare name reading a `selector`'s current value exactly as before. Teaching the existing `default` to sometimes mean "a reference" would have made `default: 'name'` ambiguous between the literal string and a lookup, with nothing in the value for the validator to discriminate on — and `default` is typed as the literal (`string` on most inputs, `bool` on `checkbox`), so the two could not even share a type. `defaultFrom` wins when it resolves, `default` is the fallback when it does not. A `checkbox` coerces explicitly — `'true'`/`'1'` are true, `'false'`/`'0'` are false — because a row's boolean arrives serialised as a string often enough to matter and `Boolean('false')` is `true`.
  - **A `blockId` carries no dot, and that is the whole reason `{id}.{field}` is unambiguous.** The new `blockId` prop type (the required `id` on both overlays, and the value of an `open` action) rejects dots and whitespace; the new `contextPath` type accepts either a bare name or exactly one dot with both sides non-empty. The dot is therefore the sole discriminator between "a selector name" and "a field of a published row", decided by shape alone rather than by looking up which of the two exists.
  - **Neither new prop type is cross-referenced against the tree, deliberately.** `open: 'edit-person'` naming a modal that is not there, or `defaultFrom: 'edit-person.nickname'` naming a field the row does not carry, both validate and are runtime no-ops. This matches how `params.from` has always resolved. Resolving references at registration would make a tree's validity depend on the order its blocks are declared in, and still could not cover the `{field}` half — a row's fields are known only once the `source` has answered.

The `{ refresh: true }` opt-in is passed only from a form's submit-success path. The desktop renderer shipped the naive version first, bumping the signal on every close, and was corrected before merge: a cancel or a backdrop click would otherwise refetch every data-bound block on the screen, turning "I changed my mind" into a burst of requests.

Note the two mutation surfaces are now deliberately asymmetric and neither is a superset of the other: **`submitSpec` is `POST`/`PUT`/`PATCH`, `dataTable.rowActions` is `POST`/`PUT`/`DELETE`.** A row action cannot `PATCH`, and a form cannot `DELETE`.

Plugin authors should expect a malformed reference to surface as a `404`/`405` from their own route rather than as a client-side error.
  - **Known divergence between the hosts, in what actually reaches the server.** The web resolves `defaultFrom` once at form mount, materialising every resolvable reference into the form's value map, so an untouched seeded input is still part of the submitted payload. That difference is invisible on a `POST` and consequential on a `PATCH` against a full-replace resource: `SyncController::update()` validates with `requireAll = true` and writes every domain column, so a desktop edit that leaves the required field untouched is a `400`, and one that edits only that field writes `null` over the columns the user did not touch. A plugin declaring a `PATCH` edit form should assume the desktop sends only edited fields until this is reconciled.

  - **Create and delete both refresh the list through the same signal**: create closes its modal on success (the overlay submit-success path), delete tombstones through the row action's `onMutated`. Neither reloads the page.
- **A plugin can register queue job handlers, so one worker runs everybody's work.** `JobInterface` and the durable queue have been public since SDK 1.0 and `JobRegistry::register()` was always callable, but nothing ever *discovered* a plugin's handlers: the shipped `queue:work` built a bare `JobRegistry`, filled it from `CoreJobs` only, and dead-lettered anything a plugin enqueued as "No handler registered for job" — `CoreJobs`' own docblock calls what it registers the "core (**non-plugin**)" handlers, so the category was anticipated and the seam was never built. The workaround a downstream team arrived at — shipping their own `queue:work` that re-registers the core handlers beside their own — works and patches nothing, but it puts **one worker process per plugin in front of one queue**, and every one of them is a place core's own queued work (notification delivery, error alerting) can be duplicated or dropped. SDK **1.28** adds `PluginJobsInterface`, the same optional-capability shape as `PluginRolesInterface`: `getJobs()` returns a bare-name ⇒ `JobInterface` map, `PluginLoader::collectJobs()` discovers it, and both ends of the queue are filled from the same object — `public/index.php` collects into the very registry `JobsApiHandler` holds, so a name `POST /api/jobs` accepts is a name the worker can actually run.
  - **Names are stamped by the HOST, never declared by the plugin.** The plugin declares `sync`; `JobRegistry::registerFromSource()` stores `acme:sync`, deriving the prefix from the plugin **name** the loader supplies — the same model as `ResourceTypeRegistry`, `HealthProbeRegistry` and `PluginSettingsRegistry`. Two plugins declaring `sync` therefore get different canonical names, so one plugin's work can never be handed to another's handler, and no declaration can produce a bare or `core.`-prefixed name: core jobs live in a dotted `core.` namespace with no colon, and a plugin's canonical name always carries one. A declared name containing the separator is refused outright — that would be a plugin writing its own prefix. The residual case (two plugin names reducing to the same slug, e.g. `Acme\Plugin` and `Globex\Plugin`) is first-registration-wins and refused **loudly**, the same rule MCP prompt names and frontend feature ids already use, so the codebase has one collision story rather than two.
  - **Submittability is declared separately and fails closed.** `getSubmittableJobs()` is keyed by the same bare names and carries the extra policy: a handler the worker can run is *not* thereby reachable from `POST /api/jobs`, matching core, where `EchoJob` opts in and the internal notification and error handlers do not. Listing a name the plugin does not ship is refused rather than ignored — it reads as an exposed surface and is not one — and a re-registration clears the previous flag first, so a plugin that withdraws a job from its submittable list on reload actually stops being exposed. A non-string entry is refused, not coerced: a plugin declaration is untrusted data, and casting it to compare turns a malformed exposure list into a plausible-looking miss.
  - **The refusal is whole-declaration, never per entry.** A half-registered plugin silently dead-letters the jobs that did not make it, which is the exact failure this interface exists to remove, reintroduced one level down and harder to diagnose than contributing nothing. `HealthProbeRegistry` refuses a batch for the same reason.
  - **Failure isolation, because the worker is infrastructure.** The process that runs plugin handlers also delivers core's notifications and error alerts. `getJobs()` throwing goes through the same lifecycle error boundary as `getMcpPrompts()` / `getHealthProbes()`; a malformed declaration is an `InvalidPluginJobException` logged as a warning; `PluginJobs::register()` wraps the whole discovery so a failure is a degraded worker, never a dead one. Either way that plugin contributes nothing and core keeps running. `collectJobs()` is also stricter than `collectMcpPrompts()` on purpose, skipping administratively disabled plugins and any not in an active lifecycle state — a disabled plugin that kept processing queued work would still be running.
  - **The plugin constructs its own handlers**, resolving what they need from the host container at declaration time, exactly as `PluginMcpInterface` and the roles interface do; nothing is injected into `handle()` beyond the payload, because the host cannot know what a plugin's handler needs. Handlers are built once and reused for every job in a persistent worker, so the SDK docs and the `HelloWorld` reference (`helloworld:greeting_digest`) both pass the PDO as a **closure** rather than a handle — a captured connection would outlive the host's own recycling.
  - **`public/index.php`'s CLI block never loaded `src/helpers.php`**, an entry-point divergence this feature surfaced by running the real worker rather than a test. `helpers.php` is a plain function file required at line 258 — in the HTTP path, after the CLI block has already `exit`ed — so every command dispatched through *that* entry point ran with **no service container at all**: `queue:work` could not register the `Database` service a plugin's handler resolves, and a plugin using the documented container seam died on `Call to undefined function Whity\register_service()` instead of failing through the loader's error boundary. `bin/whity-cli` has always loaded it, which is what made the divergence invisible.
  - **`ci-plugin-tenant-conformance.php` now scans a plugin's `Jobs/` beside its `Api/`.** A background handler queries the same tenant tables with no request behind it, so an unscoped query there is a cross-tenant read no response body would ever reveal. The queue was the one door into those tables the guard did not watch.
  - **Known limitation, deliberately not fixed here:** `collectJobs()` runs once at boot, so a plugin **enabled at runtime** through the plugins API does not reach an already-built registry until that process recycles. Workers recycle on `--max-jobs` / `--max-runtime` / `--memory` and FrankenPHP workers recycle too, so it converges rather than staying wrong; `collectMcpPrompts()` has exactly the same property today. `HelloWorld`'s `getSdkConstraint()` moves `^1.2` → `^1.28`, because a host below 1.28 has no such interface and the plugin would fatal on load rather than merely lose its job — the version gate is the mechanism for saying so.
- **A plugin's own domain events can reach the platform audit trail (SDK 1.29, `PluginEventsInterface`).** `AuditLogger::subscribe()` binds a hardcoded map of *core* event names — `role.created`, `user.updated`, `ou.role_assigned` and nine more — so a plugin dispatching its own event through the hook manager matched none of them and produced no audit row. Everything a plugin did was absent from the one screen an operator opens to answer "who did what", and the two workarounds available were both worse than the gap: writing to `audit_log` directly puts a second writer on a table whose entire design is that it has one (no metadata sanitising, no tenant resolution, and nothing stopping a row that claims to be `user.deleted`), while a private activity table is a second audit surface, in a second place, that nobody is looking at. A plugin now declares which of its events belong in the trail and the host records them through the *same* path core's rows take.
  - **Declared bare, recorded namespaced — on both halves of the row.** `'task.completed' => ['targetType' => 'task', 'idKey' => 'task_id']` is audited as action `acme:task.completed` against target type `acme:task`. The target type is namespaced for the same reason the action is: an attributable action sitting beside a target type of `user` still reads, to an operator filtering the trail, as something core did to a core record. The prefix is derived from the plugin **name the loader holds**, never from anything the declaration returns, so a plugin may declare any event it likes but cannot declare who said it — no declaration can produce the bare `user.deleted` core writes, and a declared name containing the `:` separator is refused outright as a plugin writing its own prefix.
  - **The trigger is namespaced too, and that is the load-bearing part.** The host listens on `acme:task.completed`, which is therefore what the plugin dispatches (`Events::forPlugin($this->getName(), 'task.completed')` spells it). Listening on the bare name was the obvious alternative and is unsound: the hook manager tells a listener nothing about *who* dispatched, so with two plugins declaring `task.completed` a single dispatch by one of them would have written an audit row for **both**. An audit trail that records an event which did not happen is worse than one that records nothing.
  - **`targetType` and `idKey` are both required, and `idKey` accepts an explicit `null`.** No default: `id` is right for core's payloads and wrong for most plugin ones, and getting it wrong produces a row that names an action and points at nothing *while the write succeeds* — quietly useless rather than visibly broken. An event with no single target says so out loud instead of naming a key that will never be there. At runtime the payload is data, not contract: a missing or non-numeric id records a null `target_id` rather than failing, because auditing must never break the action it records.
  - **One writer still, and the same one.** A plugin's row goes through `recordFromHook()` — core's own tenant resolution (payload `tenant_id` → hook context → system tenant), core's secret/PII filter, core's fail-soft write. Re-implementing any of that beside it is how a plugin's rows end up in the wrong tenant or carrying the token a core row would have dropped. The id key is now dropped from metadata by *name*, so a `task_id` is not stored twice and free to disagree with `target_id`.
  - **A bad declaration is contained, whole.** A `getAuditedEvents()` that throws goes through the per-plugin lifecycle error boundary; a malformed one is a logged warning. Either way that plugin's events are simply not audited and core's auditing — and every other plugin's — is untouched. The refusal is whole-declaration rather than per entry, because a plugin with half its events audited ships a trail that *looks* complete, and only an empty one is obviously empty.
  - **Disabling a plugin stops auditing it.** The subscriptions are registered with the plugin's other hooks rather than in a collection pass of their own, so `disablePlugin()` removes them and `reEnablePlugin()` restores them without a reboot — a disabled plugin still producing audit rows would be a plugin still doing something.
  - **The namespacing rule is now published** as `Whity\Sdk\PluginNamespace`, and `Whity\Core\Support\SourceSlug` defers to it. A plugin has to spell a namespaced name for itself for the first time here, and a re-derived slug is wrong exactly where it is hard to notice (`Acme\Widgets\Plugin` prefixes as `plugin`) — a dispatch under a near-miss prefix matches no listener and reports nothing at all. Qualifying under a name that yields no slug throws rather than falling back to the bare name, since an unprefixed name is precisely the shape of a core event.
  - `HelloWorld` implements it as the live reference (`helloworld:greeting.created` on greeting creation) and raises its SDK requirement to `^1.29`.
- **Taxonomy is the second feature to ship as a downloadable offline plugin, and the first to ADOPT tables core already owns rather than create its own.** Core's `tag_groups` and `tags` are live web tables; making them work offline could not mean a parallel `taxonomy_*` schema that the server would never write to. `plugins/Taxonomy` instead *adopts and augments* the existing tables — a `CREATE TABLE IF NOT EXISTS` that no-ops on the server and builds fresh on the empty offline host, plus the five sync columns via `addColumnIfMissing` — and serves them as two-way-syncable resources through the shared `SyncController` (#851). The block UI (#853) declares two `screen:'blocks'` CRUD screens (tag groups, tags) rendered identically on web and desktop. Reuses core's `tags:read`/`tags:write` slugs and `/api/tag-groups` + `/api/tags` routes (strangler-fig: inert on the server where core owns them, sole provider on the offline host). Plugin `0.2.0`, SDK `^1.27`.
  - **`display_name` is stored JSON-encoded, and that is load-bearing, not incidental.** The column is `JSONB` on the server and `TEXT` offline; a bare string like `Colors` is invalid JSON and Postgres rejects it into `JSONB`, so `TagGroupResource` writes `json_encode(trim($displayName))` (`"Colors"`) — valid for both engines — and decodes on read. Storing the raw string would have built and passed every SQLite test and then failed the first write on the server's real `JSONB` column.
  - **A tag's group is picked via `referenceSelect`, not free text**, so the two synced tables stay referentially coherent offline; cross-store id remapping for the `group_id` edge is deferred (the Relations-edges pattern), documented in code.
  - **The offline migration uses `DEFAULT (NOW())` parenthesised** — the same guard the Relations port learned the hard way (bare `DEFAULT NOW()` crash-loops the offline SQLite host, and an adopt-and-augment CREATE only ever executes there). Proven by an offline-conformance test that runs the migration on the empty SQLite host.
- **Documents is the third feature port: the Document Designer's `document_templates` and `document_blocks` sync offline.** Same adopt-and-augment shape as Taxonomy against the two identical tenant-owned tables from migration `059`, through `SyncController`, reusing core's `documents:read`/`documents:write` slugs and `/api/document-templates` + `/api/document-blocks` routes. A shared `AbstractDocumentDesignerResource` holds the common validate/toPublicFields; each table's verbatim client object (`data`, a `DocTemplate` / `DocElement[]`) is json-encoded so it is valid for both the server `JSONB` column and the offline `TEXT` column. Verified on PostgreSQL + SQLite (19 tests) + an offline-conformance test + PHPStan level 8. Plugin `0.1.0`.
  - **The block UI is list + create + delete, with NO in-UI edit — and that is a data-safety decision, not an omission.** `SyncController` UPDATE is a full-row replace (`validate($body, requireAll: true)`, every domain column written), and the `data` canvas object cannot round-trip through a block form input, so a metadata-only edit form would silently reset a template's entire design to empty. Renaming and content editing therefore belong to the canvas designer (a follow-on shared-React surface that submits the whole record); the PATCH route stays only for device sync, which always sends every field and is lossless. Shipping the edit modal with a warning was rejected — a form that wipes content on save is not made safe by a docblock.
  - **Offline-safe DDL, proven by the conformance test:** `SERIAL` not `BIGSERIAL`, `TEXT` not `JSONB`, `BOOLEAN … DEFAULT 0`, parenthesised `DEFAULT (NOW())`, and the `tenants` FK dropped from the offline build (the offline host has no `tenants` table). The server keeps core's real `059` DDL untouched because the plugin's CREATE no-ops there.
- **A desktop device can now talk to its REMOTE server, not just its local offline host — the `remote_request` Tauri command.** The desktop had exactly one transport, `php_request`, aimed at the bundled local FrankenPHP (correct for offline plugins, useless for server-owned admin pages). `remote_request(method, path, body?, headers?)` is its peer: it forwards to the enrolled remote instance with the in-memory device access token (re-exchanged once on a `401`, reusing the sync path's keychain flow), returns the same `{status, body}` shape `php_request` already speaks, and is built with a no-redirect client so a `3xx` surfaces as its real status instead of being followed into an HTML login page. This is the transport the shared admin-page work rides on. Ships with a desktop **Plugin store** screen and a `reconcile_plugins_now` command (#855).
  - **`{status, body}`, deliberately no headers.** It matches `php_request`'s `PhpResponse` exactly, so the existing adapters need no new shape. A redirect's `Location`/`Set-Cookie` are therefore not exposed; that is fine for JSON admin APIs and is the documented future change if an SSO-on-desktop flow ever needs to read a redirect target.
  - **The 401-refresh does not own the offline-lock clock.** `remote_request` is a data path; advancing the lock stays `auth_login`'s job, so a background data call can never silently reset a user's offline grace period.
- **The first core admin page — Roles — is extracted into the shared `@amroksaleh/features` package so one React screen renders on web AND desktop.** Core admin pages lived only in `web/`, importing web-only transport (`useAuth().apiClient` → the Next proxy + cookie), so the desktop had none of them. `@amroksaleh/features/roles` exports a transport-agnostic `RolesScreen` taking injected props — a `RolesAdapter` over a two-method `Transport` (`{status, body}`, matching both the web `apiClient` and the desktop `remote_request`), a resolved `can(capability)`, an optional translator `t`, and an `onNotify` — following the proven DemoCatalog adapter seam. Web keeps a ~15-line wrapper injecting the proxy adapter (#856); the desktop mounts the same screen over `remote_request` (#858). The shared 404→`not-manageable` mapping, the `{data}` unwrap and the `per_page=100` list all live once in the adapter factory.
  - **Roles was the pilot because it is the cleanest: 100% client, zero `next/*` imports, modals as local state, already RTL.** Extracting it proves the three-part path (a Rust remote transport, a shared package behind an injected adapter, a per-host adapter) at the lowest per-page cost before scoping the rest of the admin surface.
  - **The i18n seam is injected, not bound — which required unbinding the catalogue extractor, not just annotating it.** The screen takes `t` as a prop (no `useTranslation('admin')` to bind a domain), so the catalogue extractor could not attribute its 74 `admin` + 10 `common` keys and failed the drift guard. The fix mirrors how DemoCatalog already passes — typing the injected translator so the extractor early-returns on the component files — paired with file-scoped `@i18n-keys admin`/`@i18n-keys common` blocks so every key still reaches the catalogue with its English text. The Roles chrome (`ui.*`) resolves through a composite `admin`→`common` translator in the web wrapper, preserving its existing Arabic rather than regressing to English on an RTL page.

### Changed

- **The desktop template's bundled plugin root ships empty.** `HelloWorld`, `DemoCatalog`, `PrintDemo` and `UiKitShowcase` were vendored into `templates/tauri-desktop/php-host/plugins/` and therefore loaded on every device regardless of what the server's catalog said — which directly contradicts mandatory plugin sync's whole guarantee that a device runs exactly what its server entitles it to. The directory is now documented as the bundled, read-only root that exists for a **fork** that genuinely wants an always-on local plugin baked into its installer, independent of any server; everything else arrives from the catalog.
- **The device-side sync engine is no longer hardcoded to DemoCatalog.** `sync::resource::ResourceDescriptor` (key, local table, server base path, domain columns) parameterises every push/pull/conflict path, and it independently converged on the same shape the server-side `SyncableResource` settled on. The local `item_conflicts` table gained a `resource` column in its composite primary key (device migration v9) — with one syncable resource a conflict was identified by `client_uuid` alone, which stops being true the moment there are two. The wire row shape is pinned with `tenantId` as its own typed field rather than left to a catch-all, because the bridge below forwards the domain map verbatim and a stray sync-metadata field would otherwise leak into an outgoing request body.
- **A plugin's offline writes now reach the server.** Until now a write made inside the desktop's PHP host lived only in that host's own SQLite file and never left the device — the deferred hard gap in the offline story. `sync::bridge` (device migration v10) treats the local PHP host as a second "remote" and relays it against the real server over two HTTP legs through the existing proxy channel, reusing the same generalized sync functions, so both sides speak one wire contract at one path. **`ATTACH DATABASE` was evaluated and rejected**: the device DB runs WAL and the PHP host's compatibility PDO sets no journal-mode pragma, and a cross-database transaction spanning a WAL-mode and a rollback-mode database loses SQLite's own documented atomic-commit guarantee on crash — and matching the modes would still leave two OS processes sharing one file's `-wal`/`-shm` sidecars. Rust owns no table for a bridged resource; it remembers only the last-known id/version on each side. `relations/persons` is the configured bridge resource; relaying against a resource that is not installed on a device is a safe no-op that is retried next cycle without advancing its cursor.
- **The login screen has no server picker — it was added and then removed inside this release, and the removal is the shipped behaviour.** The desktop app is portable to a different whity-core instance by setting `WHITY_BACKEND_URL` in `.env` and rebuilding (with a runtime environment variable as the dev/ops escape hatch), never by a user choosing a server at runtime; the persisted `auth_state.server_url` override layer went with it and the column survives only as informational display of which backend a device enrolled against. Anyone reading the intermediate commits should not go looking for the control.
- **The offline host's vendored SDK copy was re-synced wholesale off `develop`.** `templates/tauri-desktop/php-host/sdk` had drifted behind and was missing the entire `Sync/` namespace — load-bearing, because no `SyncController`-based downloadable plugin can even load in the offline host without it — along with `Schema/`, `Settings/` and `Sql/`. Re-vendoring the whole `sdk/src/` tree byte-for-byte (this template's existing convention) rather than cherry-picking `Sync/` is what keeps the offline host's contract identical to the server's; it is also what surfaced the `DeviceRoleChecker` fatal below.
- The desktop template's updater fallback endpoint pointed at a dead `http://localhost:8000` placeholder, which additionally fails Tauri's insecure-transport check in release builds. It now matches the compile-time default backend.
- **The nine OU routes are gated on their seeded `ous:*` permissions instead of the bare `admin` role, so a plugin aliasing OU management finally has a slug to reuse.** Migration 005 seeded `ous:read/create/update/delete/assign` and migration 009 granted them, but no route ever consulted them — the grants decided nothing. Reported downstream: a plugin aliasing OU management had to either mirror `requiredRole: 'admin'` or **invent** a slug of its own, and the invented branch is the dangerous one, letting a caller holding only that plugin's permissions mutate platform-wide OUs while holding no OU permission at all. Their review caught it; the next one might not. `GET /api/ous`, `/api/ous/{id}`, `/api/ous/{id}/roles` and `/api/ous/{id}/members` now require `ous:read`; `POST /api/ous` and `PATCH /api/ous/{id}` require `ous:write`; `DELETE /api/ous/{id}` requires `ous:delete`; and the two role-assignment routes (`POST /api/ous/{id}/roles`, `DELETE /api/ous/{ouId}/roles/{roleId}`) require `ous:assign`, verbatim what migration 005 seeded it for. The `ous` navigation item follows the route it mirrors rather than drifting from it — that drift is what left these grants vestigial in the first place.
  - **`ous:create` and `ous:update` stay unwired, and wiring them naively would have `403`'d everyone — admin included.** `RoleChecker::hasPermissionForProfile()` returns `false` outright for any permission `PermissionRegistry` does not know, and the registry is populated from `CorePermissions::all()`, which declares only `ous:read | ous:write | ous:delete | ous:assign`. The literal pair migration 005 seeded was never added there, so declaring either on a route would have refused every caller no matter what the grants said. `ous:write` — seeded and granted to `admin` by migration 023 for the `useCapabilities` hook, and until now used *only* to decide whether the UI showed a write control — is the create/update slug, so the OUs admin page's capability check and server-side enforcement finally agree on the same string. `testEveryWiredPermissionIsRegistryBacked` stops anyone re-introducing the seeded pair.
  - **The permission is the WHOLE gate; `requiredRole` is cleared, and that is load-bearing rather than cosmetic.** `RbacMiddleware` **ANDs** the two checks, so keeping the role alongside the permission would leave core demanding role *and* permission while an aliasing plugin gates on the permission alone — core stricter than its own alias, and the plugin once again granting access core refuses. That is the reported hazard in mirror image. It also matches the dominant pattern unambiguously: 146 permission-only routes to 30 role-only, and nothing anywhere in `src/`, `public/`, `sdk/` or `plugins/` combining the two.
  - **No administrator loses anything, verified against a fully migrated database on both engines before any code was written.** The seeded `admin` role already holds all four wired slugs (read/delete/assign from migration 009, write from 023); had it not, declaring them would have locked every administrator out of OU management on upgrade. `testAdminRoleHoldsEveryWiredOuPermission` pins that permanently.
  - **Migration 101 revokes the base `user` role's `ous:read`**, granted by migration 009 under the heading "User role gets read-only OU permissions" and inert ever since. Going live it would have been a silent widening: every plain user would gain the tenant's OU tree, its OU role assignments and — through `GET /api/ous/{id}/members`, which joins `profile_emails` and `roles` — the login email, display name and role of **every active member**. The product settled the other way, pinned by `web/e2e/matrix-core-areas.spec.ts` and `web/e2e/regular-user.spec.ts`, which both assert the OU nav link is absent for `user`. `down()` restores the grant, so the pair is reversible.
  - **Operator-defined roles holding `ous:*` are deliberately untouched, and this is what an operator running a custom administrative role needs to read.** The gate is now what a role *holds*, not what it is *called*. A custom role granted `ous:read` or `ous:write` at some point could not use those grants — the routes wanted the literal `admin` role — and on this release it can. So can a role that merely *inherits* from `admin` in the role hierarchy: `hasRoleForProfile()` compares role **names** and never expands the hierarchy, whereas `hasPermissionForProfile()` does, so a child-of-admin role was refused by the old gate and is admitted by the new one. Those grants becoming effective is the *point* of the change, not a side effect of it — but it means every existing `ous:*` grant outside the seeded `user` role should be confirmed as one you still mean. In the other direction, an administrative role whose `ous:*` grants were pruned at some point now loses OU management, where before the role name alone carried it.
  - **The OpenAPI spec is unchanged and no typed client needs regenerating.** `SchemaGenerator` maps a role gate and a permission gate to the same `bearerAuth` security, so the declared permission never reaches `openapi.json`; `CoreApiSchemas::ouRoutes()` moves from `adminRoute()` to `permissionRoute()` purely so the source of truth records which slug gates which route.
- **The back-merge PR that a release opens has a window, and now says so** — in `CONTRIBUTING.md` and in the PR body `release.yml` generates. Strict branch protection requires a PR's HEAD to be up to date with its BASE; this one's head is `main` against a base of `develop`, so it is mergeable only while `main` still contains everything `develop` does — the moments immediately after the release, and nothing said that anywhere. v0.2.2's back-merge hit exactly this and had to be closed.
  - **The obvious recovery is the wrong one.** `gh pr update-branch` on a stale back-merge merges `develop` **into** `main`, pushing unreleased work onto the release line. Someone reaching for the usual fix would publish code that was never released, so the documentation names that command and says not to use it here.
  - **Closing a stale one is correct and costs almost nothing** — verified rather than assumed: the merge commit it carries has a tree **identical** to its develop-side parent, which `develop` already contains, so `main` introduces no content `develop` lacks and every later `develop → main` merge is still clean. The loss is cosmetic: `git` reports `develop` as N behind after N releases, which misleads a reader but breaks nothing. This corrects the generated PR body's own earlier claim that skipping the back-merge lets the gap "compound" — the count grows, the content does not diverge.

### Fixed

- **`GET /web-build` can identify the bundle it serves. In the published `whity-core/web:v0.2.2` image it could not, and answered `200` while saying nothing.** 0.2.1 added that endpoint for one purpose: comparing its `core_version` against `/api/health`'s `version` is the only way an API/UI version mismatch is observable **from outside the box**, and the release notes prescribed exactly that two-probe check as the cheapest alarm for a half-applied update. On the shipped image `build_id`, `commit` and `core_version` all came back **null**, so anyone following that instruction — operators and downstream teams alike — was running a check that could never fail and never pass. Both of its sources were absent from an image build *by construction*: the Docker build context is a copied tree with **no `.git`**, so `next.config.ts`'s `git rev-parse HEAD` fails, and `src/` was never copied, so nothing could read `CoreVersion::VERSION`. The fields were not merely unset — no image build could ever have set them. `release.yml` now passes `WHITY_BUILD_COMMIT=${{ github.sha }}` as a build arg, `web/Dockerfile` accepts it and copies the single file the version is read from, and `web/Dockerfile.dockerignore` re-includes `src/Core/CoreVersion.php` one ancestor level at a time (a bare `!src/Core/CoreVersion.php` after `*` matches nothing, per that file's own note).
  - **The guard matters more than the fix.** A `200` was never the property worth checking: an endpoint answering with nulls reads as *working* to anything watching it, which is precisely how this reached a release and then a customer's upgrade. The release smoke job now asserts the **content** of `/web-build` — `build_id`, `commit` and `core_version` must all be non-empty — against the **published** image it pulled, so a build that cannot say what it is fails the release instead of shipping.
  - **The `Dockerfile` fails its own build on an empty `BUILD_ID`**, so a missing identity surfaces at the line that caused it rather than three jobs later in a smoke test that then has to be diagnosed backwards.
  - **Nothing retroactively fixes a published image.** `whity-core/web:v0.2.2` still cannot self-identify; until a deployment is on this release, the answer is `docker exec <web> cat /repo/web/.next/BUILD_ID` — the shell-only procedure the endpoint exists to replace, and one an operator without shell access to their own deployment cannot run at all.
- **The OU tree and all three OU pickers load every organizational unit instead of the first page. On the reporting instance — 48 units — 23 were invisible everywhere OUs are shown, and nothing said so.** `web/app/(protected)/admin/ous/page.tsx` and the three pickers each issued one `GET /api/v1/ous` with no pagination and rendered whatever came back; `PaginationParams::DEFAULT_PER_PAGE` is **25**. The failure was silent by construction rather than by accident: `buildOuTree()` re-roots a child whose parent did not arrive and draws a parent whose children did not arrive as a leaf, so a truncated hierarchy renders as a legitimate one — a faculty simply showed fewer departments than it had, with no truncation indicator anywhere — and a picker just omits the option. It reached us as **"the department was never created"**. The unit existed, was correctly parented, and was on page 2. A pagination default read as data loss.
  - **Every page is fetched, not a bigger page.** `per_page` is hard-clamped to `PaginationParams::MAX_PER_PAGE = 100` server-side, so `?per_page=100` only moves the cliff to 101 units. `web/lib/api/fetch-all-pages.ts` follows the `pagination` envelope to the last page and returns a discriminated result whose `complete` flag callers **must** branch on — that requirement is what keeps the failure loud. It lives in `web/lib/api/` rather than beside the page because ~10 other admin screens use the same `per_page=100` idiom and carry the same latent cliff at 101 rows. The termination and completeness rules — the parts that are easy to get subtly wrong — live in a single private `walkPages()`, with `fetchAllPages()` (raw `fetch`, where failure is a non-ok `Response`) and `fetchAllPagesTyped()` (openapi-fetch, where failure is an undefined `data`) as thin adapters. The typed one takes the request as a **closure** rather than a path string, because openapi-fetch derives the response type from the path literal at the call site and a path threaded through a helper would lose it. There is now exactly one implementation of the walk, not four.
  - **No surface presents a partial list, and each one decides separately what to do instead.** The **tree** throws on an incomplete walk and renders an error panel naming the size of the gap ("Loaded only 100 of 240 organizational units.") with a retry; it also pre-empts the empty state, because "No organizational units yet" over a failed fetch is the same lie as a truncated tree. **`admin/users/use-ou-options`** — the picker that assigns a person to an OU, and the consequential one of the three — withholds the options entirely and disables the picker with the gap stated inline. Disabled rather than absent: the rest of the form still edits the role safely, and an inert picker keeps the user's existing `ou_id` (the form's default) rather than clearing it. Choosing from a short list writes the wrong OU onto a real person, which is a durable, silent, wrong write. **`admin/delegations/create-modal`** keeps the dialog usable, since scoping is optional and a tenant-wide delegation is still a complete, deliberate choice that should not be blocked over an unrelated fetch — but the only fallback the form offers is **broader** than the OU scope the grantor was reaching for, so the alert says exactly that instead of leaving an empty-looking dropdown to shrug past, and a rejected load now marks the picker failed too (an empty scope list is the same lie as a short one). **`admin/settings/security`** keeps the OU-scoped 2FA option *selectable*, so the reason is discoverable where the admin is looking for the missing unit rather than greyed out with no explanation, and disables the OU select itself; submitting is already impossible while no unit is chosen, so an OU-scoped policy can never be created against a short list and enforce 2FA on the wrong part of the organization.
  - **`?parent_id=` was accepted and silently discarded**, so a caller that filtered a subtree got the whole tenant and could not distinguish an ignored filter from one that matched everything. Implemented rather than rejected: no endpoint in `src/Api/` rejects unknown query keys, so a bespoke `400` here would invent a convention that exists nowhere else, while `group_id` on `TagsApiHandler` is an exact precedent for the filter. Same shape as that precedent — snake_case, empty value means absent, non-digit is a `422`. `parent_id=0` selects the roots, since no OU has id 0 and a query string otherwise cannot express `IS NULL`. The pagination envelope counts the **filtered** set and the tenant predicate still applies, so the filter is not a cross-tenant read primitive.
  - **`perPage` and `limit` are not accepted, and no aliases were added.** `per_page` is what `PaginationParams` reads at all 13 call sites, so accepting aliases here would make `/api/ous` the only endpoint in the platform that does; `perPage` is output-only (the response envelope is camelCase) and `limit` appears nowhere as a request parameter. The answer is therefore documentation: `/api/ous` previously declared **no** query parameters at all, and now documents `page`, `per_page` and `parent_id`, states plainly that `perPage` and `limit` are not accepted, and warns that a client needing the whole hierarchy must follow the envelope.

## [0.2.2] - 2026-08-16

### Added
- **A resource's role grants can be cleaned up in one call when the record is deleted.** `DELETE /api/resource-role-grants/all?resource_type=T&resource_id=N` revokes every grant addressed at one resource. `ResourceRoleAssignmentRepository::revokeAllFor()` already existed but had no route, so the first consumer to delete a record carrying grants had to hand-roll list-then-revoke-each — the loop this surface exists to eliminate, and one that leaves the resource half-cleaned if it dies midway. Nothing removes these rows automatically: `resource_id` carries no foreign key, so core is never told a record disappeared and a later record reusing that id silently inherits authority granted to a dead one.
  - **A distinct `/all` path**, mirroring `DELETE /api/entity-tags/all`, rather than an argument-shape variant of the by-id revoke. The path segment says "every grant here" out loud, and a malformed single-revoke can never degrade into "remove everything". `all` is never `\d+`, so the two routes cannot collide.
  - **Returns the number of grants revoked**, not a bare `204`. Because 0 is a success, a bare confirmation would leave the caller unable to tell "wiped 7 grants" from "wiped nothing because I addressed the wrong record" — the one distinction a cleanup path needs in its log, and the thing that makes the call verifiable.
  - **Idempotent: a resource with no grants is `200` / `revoked: 0`, never `404`.** The caller is deleting a record and neither knows nor cares whether it carried grants, so the cleanup has to be safe to call unconditionally and safe to retry. That property is the entire point of the route.
  - **It deliberately does NOT ask the owning plugin to vouch for the resource**, unlike the create route, which fails *closed* when nobody does. By cleanup time the record is usually already deleted, so nobody *can* vouch — a fails-closed ownership check would refuse exactly the calls that matter, stranding the rows at an id a later record will reuse, and would make cleanup impossible while the owning plugin is disabled. Skipping it grants nothing new: the `DELETE` is tenant-scoped, so the blast radius is rows the caller could already have listed and revoked one id at a time, and a delete can only ever *remove* authority, never confer it.
  - **`resource_type` is still validated** against `ResourceTypeRegistry` (`422`), for the opposite reason ownership is not: a typo would otherwise answer `revoked: 0`, indistinguishable from "that record had no grants", so the caller logs a successful cleanup that removed nothing while the real rows survive. It also keeps this route's parameters and validation identical to the list route's, so `GET` and `DELETE .../all` always address exactly the same rows.
  - Gated on the existing `roles:manage` — the same reasoning as the routes it joins, and bulk cleanup removes strictly more than a single revoke, so anything weaker would make `roles:manage` avoidable by asking for everything at once. Announced as `rbac.resource_grant.revoked_all` (a distinct event, because this route deliberately never collects the individual ids) when it actually removed something. No UI: a platform capability consumed by plugins over HTTP, like `/api/entity-tags/all`.
- **Resource-scoped role grants can now be written, not only read.** Migration 088 and `PermissionResolver` shipped the *resolution* half of per-record authority — a plugin could ask "does this profile hold this role at this record?" — but no HTTP route created, listed or revoked a `resource_role_assignments` row. The only way to grant one was an unversioned, unvalidated write straight at a table whose `resource_id` is deliberately not a foreign key, so adopters kept their own per-record role table instead: reading authority from the platform while writing it into their own storage leaves two sources of truth for one question, which is worse than the private table this design set out to eliminate. `POST`/`GET`/`DELETE /api/resource-role-grants` close the gap.
  - **`profile_id`'s nullability is the meaning, and both shapes are first-class.** Omitted or `null` grants the role to *everyone at this resource*; a value grants it to *that one profile here*. Both are creatable, both come back in one list distinguished by that column, and the table's two partial unique indexes keep them independent — repeating the everyone-grant is not satisfied by an existing profile-grant for the same role, which would otherwise hand the caller narrower authority than it asked for while reporting success.
  - **A repeat grant is a success, never a `409`.** It answers `200` with `created: false` and the id of the row that already says it, mirroring `POST /api/users/{id}/memberships`. Treating "the thing you asked for is already true" as an error forces every caller to hand-roll a read-before-write that races against a concurrent grant anyway.
  - **Revoke is addressed by grant id**, not by `(resource, role, profile)`. Over HTTP an omitted `profile_id` and an explicit `null` are indistinguishable, so a tuple-addressed revoke lets a dropped parameter silently revoke *everyone's* grant when one profile's was meant — a widening of the blast radius produced by a typo. An id names exactly one row, and the ids come from the list route.
  - **`resource_id` is validated against the caller's tenant**, which nothing else does: the column carries no foreign key because the target table varies by `resource_type`. Core checks `ou` directly; a plugin type is checked by asking its owner through the new `rbac.resource_grant.verify_resource` filter hook. It **fails closed** — with nobody vouching the grant is refused rather than written against an unvalidated integer, because ids get reused and a grant left at a stale id is silently inherited by whatever record takes that id next.
  - **`resource_type` is validated against `ResourceTypeRegistry`** and an unregistered type is rejected at the boundary (`422`) rather than stored: a typo would otherwise create authority nothing ever resolves — failing *closed*, but invisibly to the operator who wrote it.
  - **Only the tenant's own roles and globals are grantable**, so a resource grant cannot become a way to attach another tenant's private role, one role id at a time. A role outside that set is `404`, never `403`, so cross-tenant role existence is never disclosed — the same rule and the same reasoning as OU role assignment.
  - **Gated on the existing `roles:read` / `roles:manage`, deliberately not a new permission.** A new one needs a grant migration, and such a migration reaches the `admin` role only — so every operator running a custom administrative role would silently not have a capability their plugins depend on.
  - **A grant widens authority at one resource and never substitutes for membership.** Resolution still gates on an ACTIVE membership in the tenant *before* consulting resource grants, so a grant cannot become a back door into a tenant. Granting is therefore restricted to profiles that belong to the tenant, and the rule is pinned by a test that grants to a suspended member and asserts the permission is still refused, with a positive control on an active one.
  - **No UI ships with this**, which is the intended end state rather than an omission: it is a platform capability consumed by plugins over HTTP, like `/api/entity-tags`. A core screen would have to render a record picker per resource type, and only the plugin owning that type can do so.

### Added

The rename **moves the existing row**: same profile, same credential, same tenant-0 admin membership, never a second account. Unset variable ⇒ strict no-op. An address another identity already holds ⇒ reported and skipped, because colliding two accounts to honour an environment variable is worse than leaving the rename undone.
  - **`Seeder::seed()` calls the same reconciler**, so an operator who only decides to rename *after* 095 has already run (as a no-op) sets the variable and re-seeds, instead of being told to `UPDATE` rows by hand. Deliberately narrow: it only ever moves an account off the historical default — renaming an administrator that already has a real address is `PATCH /api/users/{id}`'s job, so re-pointing the variable a second time is a no-op by construction rather than a surprise write.
  - **`admin@example.com` / `user@example.com` / `superuser@example.com` are seeded only under `APP_ENV=development`** (or with the explicit `seed --with-fixtures`). A production or staging seed could previously materialise three known-address accounts holding real credentials that nobody asked for; the release smoke job has *documented* the seeder as "a no-op outside development" since before it was one. An unset `APP_ENV` counts as not-development, matching every other environment-gated guard here. The bootstrap administrator is unaffected and is still seeded everywhere.
  - **A configured password that cannot take effect is now reported.** The seeder skips an account whose `profile_email` already exists — that is what makes re-seeding safe — but it also meant an `INITIAL_*_PASSWORD` set *after* the first seed was silently inert: the documented variable present, the account authenticating with something else, and nothing anywhere saying why (observed on an install where `superuser@example.com` authenticated with the value of a *different* variable). Seeding now says so, naming the account and the variable, and still refuses to rewrite the stored hash — a seed run that silently reset a live administrator's credential would be a credential reset wearing a seeder's clothes. Passwords are also resolved lazily now, so a re-seed no longer announces a freshly generated password for every account it then leaves alone.
  - **`seed` is registered in `whity-cli`.** `migrate` was reachable through that tool and `seed` was not, so the only bootstrap an operator following the CLI could produce was the migration-seeded administrator — the one account nothing let them configure.
  - **`INITIAL_SYSTEM_ADMIN_EMAIL` is passed through in all three compose files**, including the dev `frankenphp` service, which carried none of the `INITIAL_*` variables even though `docker exec whity_frankenphp php public/index.php migrate run` is the flow the README and the go-live checklist document. Compose environments are enumerated, not inherited, so a variable absent there is a variable that silently does not exist for that command — a configurable address unreachable from `.env` would have reproduced the exact failure this change removes.
  - **Retiring the bootstrap account is documented** (`docs/wiki/Go-Live-Checklist.md`): `PATCH /api/users/{id}` with `accountStatus: "inactive"`, which `AuthHandler` refuses to authenticate — with a generic `401` so the account cannot be enumerated — plus the ordering that makes it safe (a second tenant-0 administrator with a verified, routable address must exist first). That mechanism was previously inferable only from reading `AuthHandler`.
- **A deployment's version state is now observable — including the half that was lying.** A real 0.1.0 → 0.2.0 update passed the documented success criterion (`/api/health` reported `version: 0.2.0`, `status: ok`) while the UI a user actually saw was built five days and 268 frontend commits earlier, and nothing anywhere reported the mismatch. The mechanism: a web start command that builds only when `.next/BUILD_ID` is **absent** asks "does a build exist?", never "is it *this* build?", so a restart after a checkout silently re-serves the previous bundle. Reading the truth required `docker exec <web> cat /repo/web/.next/BUILD_ID`, which means an API/UI version mismatch was undetectable from outside the box — including by monitoring.
  - **`GET /web-build`** (unauthenticated, served by the **web** tier) reports the served bundle's `build_id`, `commit`, `built_at`, and the `core_version` it was built alongside. It lives on the web service, not in `/api/health`, because only the process that loaded a bundle knows which bundle it loaded: an image deployment's backend has no `.next` to read at all, and in a bind-mount deployment the file on disk is not necessarily what the running Next process loaded at boot — which is *precisely* the incident. A backend-sourced field would have been confidently wrong exactly when it mattered. The check is therefore two cheap probes against one origin: **`/web-build`'s `core_version` must equal `/api/health`'s `version`**, and comparing them is the cheapest available alarm for a half-applied update.
  - **`BUILD_ID` is now the commit.** `generateBuildId` pins it to `git rev-parse HEAD` (overridable with `WHITY_BUILD_COMMIT` for image builds with no `.git`), so a build output is traceable to a source revision and the freshness question becomes answerable rather than guessable. Where no commit can be determined the value is reported as `null` — never as an empty string or an invented one.
  - **`scripts/start-web.sh`** rebuilds when the built commit differs from the checked-out one, not only when no build exists. When either side is unknown it **rebuilds anyway**: a needless rebuild costs minutes, while serving a stale bundle costs an outage nobody can see. `WHITY_FORCE_BUILD=1` forces it.
- **Platform version state over HTTP, for operators who have no shell.** `GET /api/v1/platform/version` reports the running `core_version`, `sdk_version` and `php_version` — the plugin SDK contract version appeared in no endpoint at all until now, despite being the number that explains a plugin refusing to load after a core update. `GET /api/v1/platform/version/latest` answers the same latest-release comparison `update:check` runs. On a white-label platform the operator is the *customer*, quite possibly without shell access to their own deployment, so "what version am I on, and is there a newer one?" is a product feature rather than a sysadmin task.
  - **System tenant only** (`settings:manage` **and** tenant 0, the second half enforced in the handler): this describes the whole deployment, which on a shared install is none of a tenant admin's business — and nothing they could act on, since updating is a host-level operation.
  - **`check_failed` is a `200`, not an HTTP error.** "I could not tell" is information, and collapsing it into an error status is how a naive caller comes to read it as "up to date". Statuses are `up_to_date`, `update_available`, `ahead`, `no_releases`, `check_failed`, with a plain `update_available` boolean alongside for callers that would rather not hard-code the vocabulary.
  - **Read-only, deliberately.** There is no "apply update" action: applying means fetch + checkout + migrate + rebuild for a source deployment and something else entirely for an image deployment, whose running container cannot replace its own immutable image — and a one-click apply in front of an unreliable pre-flight is a one-click outage. The apply step stays the runbook.

### Changed
- The release comparison moved out of the `update:check` command into `Whity\Core\Update\LatestReleaseCheck`, which returns a `ReleaseCheckResult` value object. The CLI is now a renderer over that verdict (identical output, identical exit codes `0`/`1`/`2`) and the HTTP endpoint serialises the same one — a second implementation would eventually disagree with the first, and the whole point of this surface is that it can be trusted.
- [`docs/wiki/Core-Update.md`](docs/wiki/Core-Update.md) gains the frontend rebuild step, and its verification step now covers **both** tiers: `/api/health` alone is not a success criterion, having already passed while the UI was hundreds of commits stale. It also records that clearing a named-volume `.next` requires removing its **contents** (`rm -rf .next/* .next/.[!.]*`) — `rm -rf .next` fails with "Device or resource busy" even in a fresh one-off container, because the volume is mounted *at* that path.

## [0.2.0] - 2026-08-14

### Added
- **Bulk data-type lifecycle operations, with SKIP-AND-REPORT semantics.** `POST /api/data-types/{type}/bulk` takes `{"action": "trash|restore|retire|delete", "ids": [...]}` and performs one action over many records. Adopters building "empty the trash" and "bulk retire" screens were looping over the single-record calls — correct, and still sanctioned, but N HTTP round trips for one user gesture; the alternative they must never reach for is one bulk `UPDATE`, which bypasses every guard, every veto and every hook at once, silently. This is the supported middle. It answers the question #743 left open, and answers it **skip and report**: a refused record does **not** abort the batch. Clearing 493 of 500 items and reporting why 7 refused is the intended outcome; an empty-trash that fails entirely because one item is still referenced is the failure mode being removed. See [`docs/wiki/Plugin-Data-Types.md`](docs/wiki/Plugin-Data-Types.md).
  - **Each record is its own transaction, its own veto point and its own audit row.** A refusal on record 7 leaves records 1–6 *committed* — not pending, not rolled back — so there is deliberately no transaction around the batch (one would reintroduce all-or-nothing through the back door and hold a lock for the whole run). `datatype.lifecycle.changing` fires per record exactly as it does for a single call, so a plugin refusing one record has no effect on the others. Audit stays one row per record, matching the single-record path: "who deleted this record" is answered by the same query regardless of which entry point was used, which a single batch-shaped row could not do. Bulk therefore saves round trips and request overhead — **not** transactions, hooks or audit rows, each of which is a guarantee rather than an overhead.
  - **One refusal vocabulary, not two.** Every id is routed through the same `GatedDataTypeLifecycle` mutator the single-record endpoint and the SDK write contract use, so a per-record refusal carries the existing keys (`still_referenced`, `composition_still_referenced`, `trash_before_deleting`, `retired_records_are_permanent`, `blocked_by_plugin`, `not_found`, …) with the same `message`, the same `blockers` and the same `state`. Each result entry also carries the `status` its single-record call would have answered, so a client already rendering (status, reason) pairs reuses that code unchanged. A test asserts the two paths agree case-by-case across the whole vocabulary, including that an idempotent no-op stays a *success* in bulk.
  - **`200` whenever the batch ran — including an all-refused batch**, whose `counts.ok` is simply `0`: the status describes the operation ("attempt these and report"), which succeeded. `207 Multi-Status` is the apt code and is deliberately not used — too much of the stack between an API and a browser funnels anything that is not `200` into an error branch, and a bulk call landing in an error handler sends an adopter straight back to the loop. Non-`200` means the batch never ran: `404 unknown_data_type`, `405 <action>_not_offered` and `403 insufficient_permissions` are per *(type, action, caller)* rather than per record and are answered **once**, in the same envelope and under the same key the single call publishes; plus `400 unknown_action` / `400 invalid_ids` and `422 batch_too_large`.
  - **Bounded by a setting, not a constant.** The new `data_types.bulk_max_ids` (per-tenant overridable, default **500**) caps one request — an unbounded id list is a denial-of-service with a polite name. Exceeding it is a `422` naming the limit, **never a truncation**: a client that asked to clear 900 records and was quietly given 500 has no way to notice the other 400 are still there. Duplicate ids are collapsed (first occurrence wins, one attempt and one result entry), with `counts.requested` and `counts.unique` both published so the de-duplication is visible.
  - **No `bulk()` on the `DataTypeLifecycle` SDK contract, and that is now a decision rather than an open question** — the SDK is unchanged and stays at 1.26. The endpoint's value is amortising HTTP round trips, which an in-process caller does not pay; a contract method would be a three-line loop wearing a permanent compatibility promise, and would have to publish a second result shape into a contract whose present strength is that `LifecycleOutcome` is the very object the endpoint answers with. In-process bulk work stays a loop over the single-record calls, which already gets identical gating, its own transaction per record, and identical reason keys.
- **Plugin SDK 1.24 — a supported way to PERFORM a lifecycle transition, not only to ask about one.** Core told adopters to route their lifecycle writes through core and then published only the read-only `Whity\Sdk\DataType\DataTypeGuard`, so a plugin that needed to actually trash a record duck-typed `Whity\Core\DataType\DataTypeLifecycleService` — a host internal with no contract and no compatibility promise. That is core's fault, not theirs. The new `Whity\Sdk\DataType\DataTypeLifecycle` exposes `trash` / `restore` / `retire` / `delete`, registered in the container by **both** entry points (`public/index.php` and `BaseCommand::setupKernel()`). `DataTypeGuard` is untouched and gains no mutators: "holding this confers no authority" is the one sentence that makes it safe to hand out, so writes get a *second* contract rather than being smuggled into the first.
  - **An in-process call cannot skip a check the endpoint enforces**, and not because two implementations were written to agree: `DataTypesApiHandler` performs no authorization of its own any more, and both paths call the same `GatedDataTypeLifecycle`. A type the caller may not read is reported **unknown** (`404`), never forbidden — holding the contract must not become a way to enumerate the catalogue; an action the type does not offer is `405`; a missing permission is `403`, resolved through the same `RoleChecker` the RBAC middleware uses. `$actorProfileId` is **required**, because it is the subject of the permission check and the actor on the audit entry — an optional one could only fail closed or run ungated.
  - Transitions answer with `Whity\Sdk\DataType\LifecycleOutcome` — the *same object* the HTTP layer builds its response from, so `reason` (the stable key), `message` (the fallback sentence), `blockers` and `httpStatus()` are one vocabulary across both call paths rather than two kept in step by hand. Every refusal the generated endpoints answer now carries `details.reason`, including the authorization ones (`unknown_data_type`, `<action>_not_offered`, `insufficient_permissions` — the last still naming the missing slug in `details.required`); the `403` previously carried no reason key at all.
  - **In-process bulk lifecycle work is a LOOP over single-record calls** — that is the sanctioned pattern, not a stopgap. The tempting alternative, one `UPDATE … WHERE status = 'trashed'`, bypasses every guard, every veto and every hook at once, silently. No bulk method ships on the SDK contract; the batch question this release left open ("does one veto abort the batch, or is that record skipped and reported?") is answered by the **skip-and-report** `POST /api/data-types/{type}/bulk` endpoint above. See [`docs/wiki/Plugin-Data-Types.md`](docs/wiki/Plugin-Data-Types.md).
- **A data type can now declare what a record is COMPOSED OF, not only what references it.** `blocks_delete` names rows that must *outlive* a record; the new `cascade_delete` names rows that are *part of* it and are deleted with it. `DataTypeLifecycleService::delete()` ran exactly one statement — `DELETE FROM <table> WHERE <key> AND <tenant>` — and with no foreign keys between plugin tables (the convention here, and the reason declared guards exist at all) nothing removed a record's children either, so deleting through `DELETE /api/data-types/{type}/{id}` left them pointing at an id that no longer resolved, in a state no screen lists and no guard protects. It answered `200`. Reported by an adopter, who worked around it in a `changing` listener; that listener can now be deleted. The declaration takes the same shape and passes the same `TableOwnershipRegistry` gate as a guard — a plugin cannot declare composition over a table it does not own, and the gate matters more here because a guard turns a declaration into a `COUNT` while a cascade turns it into a `DELETE`. Children are deleted before the parent, inside the transition's own transaction (joining an open one rather than nesting), with `tenant_id` bound on every statement; the remembered restore state of every owned row that is itself a declared type is forgotten with it. `ignore_when` is **refused** on a composition (a cascade that skipped rows would orphan exactly what it exists to remove), as are a table declared in *both* lists and a type cascading onto its own table. See [`docs/wiki/Plugin-Data-Types.md`](docs/wiki/Plugin-Data-Types.md).
  - Core **refuses** rather than cascading in three cases, all checked before any write and all predicted exactly by the pre-flight endpoint: `cascade_would_nest` (an owned table that declares a composition of its own — **nesting is not supported in this pass**, and doing one level silently would orphan the level below; refused at delete time rather than at registration, because it is a fact about two declarations and rejecting whichever registered second would make the outcome depend on plugin load order), `composition_is_permanent` (an owned row is retired, and retirement is permanent), and `composition_still_referenced` (an owned row is protected by its own type's `blocks_delete` — deleting it through the parent would defeat a declared guard from above). The last is a distinct key from `still_referenced` because the two send a caller to different places.
  - `GET /api/data-types/{type}/{id}` gains a **`cascade`** array — what this delete would *also* remove, with each declaring plugin's own label and a count — so a confirmation can say "this will also delete 4 line items" instead of destroying them silently. It is a third question and stays apart from `blockers` and `refusals`: a record with composition is still `deletable`. Edges with no rows are omitted, so `[]` means "nothing else goes". `GET /api/data-types` round-trips `cascade_delete` beside `blocks_delete`; a delete's audit entry records what went with it under `metadata.cascaded`.
- **A role can now be ASKED about at one record, not only granted at one.** Plugin SDK 1.22 gives `Whity\Sdk\Rbac\PermissionResolver::hasRole()` the same optional `$resourceType` / `$resourceId` pair SDK 1.17 gave `hasPermission()` and `effectivePermissions()`, and `RoleChecker::hasRoleForProfile()` passes them straight through. The capability already existed one layer down — `RoleChecker::getEffectiveRolesForProfile()` has honoured a resource scope since the polymorphic `resource_role_assignments` table landed — but `hasRoleForProfile()` called it with no resource arguments, so "this profile holds role X at record A and role Y at record B" was fully representable in storage, fully resolvable by the machinery, and unreachable through the method any caller would naturally use. An adopter reasonably read that asymmetry as meaning per-record role holding required a schema change to `memberships`; it does not, and `memberships` keeps its `UNIQUE(profile_id, tenant_id)` shape unchanged (multi-role membership remains a separate, open question). Everything the permission side already guarantees holds identically for roles: the pair is **additive** (omitting it preserves the previous tenant-wide answer exactly, so every existing three-argument caller — `RbacMiddleware`, the MCP handlers, the settings and navigation handlers — is unaffected), a **half-specified** scope collapses to no scope (matching one column and ignoring the other would return grants from the *wrong* resource), the scoped answer is a **superset** of the unscoped one, and a resource grant is **never a substitute for tenant membership** — a profile with no active membership resolves to nothing whatever is granted at the record. The route-level `requiredRole` gate is deliberately untouched and stays flat and tenant-wide: it runs before the handler with no record in hand, so a record-scoped grant cannot silently open a whole route. See [`docs/wiki/PERMISSION_SYSTEM.md`](docs/wiki/PERMISSION_SYSTEM.md).
- **A plugin can now REFUSE a data-type lifecycle transition, not only watch one happen.** The new `datatype.lifecycle.changing` hook is dispatched *before* the write for **all four** mutating actions (`trash`, `restore`, `retire`, `delete`), carrying the same payload as the existing post-transition `datatype.lifecycle.changed`; `to` describes where the record is about to go (`null` for a delete). A listener throwing `Whity\Sdk\Hooks\HookVetoException` aborts the transition: nothing is written, no `changed` event fires, no audit entry is recorded, and the caller receives `409 Conflict` with `reason: "blocked_by_plugin"` and the veto's own `reason()` as the message — never its raw `getMessage()`. The hook is dispatched *inside* the transition's transaction, so a listener that wrote before a later listener vetoed is rolled back with it; when the caller already holds a transaction open, core joins it rather than nesting and never ends a unit of work it did not begin. A veto does **not** count toward the plugin failure breaker — a plugin refusing a transition is working correctly, and a disabled plugin would silently stop refusing. Any other `Throwable` from a listener stays isolated by the per-plugin error boundary and the transition proceeds, exactly as before. This exists because core's refusals are the ones core can *derive* (a declared `blocks_delete` guard counts rows, and it governs `delete`, not `trash`), which leaves a domain rule — "something downstream depends on this record" — with no expression but a parallel route in front of core's, and therefore two lifecycle memories for one record that disagree about where a restore lands. Requested by an adopter. See [`docs/wiki/Plugin-Data-Types.md`](docs/wiki/Plugin-Data-Types.md).
  - **Known and documented limitation:** the pre-flight `GET /api/data-types/{type}/{id}` predicts **core's** refusals completely and exactly, and *cannot* predict a plugin veto — it deliberately does not dispatch the hook, because a `GET` must not run plugin listeners (surprising, potentially side-effecting, and a "no veto" prediction expires immediately). An action published as available can therefore still answer `409 blocked_by_plugin` when attempted; clients should render controls from `refusals` and stay able to surface that `409`.
- `Whity\Core\DataType\LifecycleStateMemory` is now registered in the service container by **both** entry points (`public/index.php` and `BaseCommand::setupKernel()`), as the lifecycle service's own instance. A plugin that hard-deletes a record *outside* core can clear its remembered restore state with `\Whity\app(LifecycleStateMemory::class)->forget($type, $tenantId, $id)` instead of hand-writing a `DELETE` against a core-owned table; previously the class existed but was unreachable (the container refuses to build it — it takes a `PDO`). `record_id` carries no foreign key, so an orphaned row is inherited by whatever record next occupies that key — for a client-supplied key, a later record can be restored into a state it never held. It is deliberately **not** on the read-only `DataTypeGuard` contract: `forget()` writes, and that contract's guarantee is that none of its methods do.
- Plugin SDK 1.20 — plugin-owned **data types** (`registerDataType`, "Door 2" of the schema-driven admin surface). A plugin declares, as data, where a record lives, what its lifecycle states mean, and which rows still point at it; core enforces the rest. New optional contracts: `Whity\Sdk\Tenant\PluginTablesInterface` (which tables the plugin owns — the host stamps *who* owns them from the plugin name the loader supplies, so a plugin can claim any table name but never claim to be somebody else), `Whity\Sdk\DataType\PluginDataTypesInterface` (the lifecycle + reference graph), and the read-only `Whity\Sdk\DataType\DataTypeGuard`, so a plugin keeping its own delete route enforces through the same evaluator the generated one uses. Existing plugins are unaffected. See [`docs/wiki/Plugin-Data-Types.md`](docs/wiki/Plugin-Data-Types.md).
- **Trashed and retired are distinct lifecycle states**, not two spellings of "soft deleted". *Trashed* is a mistake: reversible, and removable for real once nothing references it. *Retired* is a record that served its purpose: closed to new references, permanently readable, never restorable and never deletable — because rows that already reference it still need it to resolve. Core refuses every transition that would collapse the two.
- **Declarative referential guards**: `blocks_delete` names the tables and columns that reference a record, plus the human label a refusal should use. A delete that would orphan referencing rows is refused with `409` naming what blocks it ("Still referenced by 3 catalogue notes"), at every enforcement point rather than wherever a plugin remembered to check. A referencing row that is itself trashed can be declared not to block.
- Generated lifecycle endpoints for every declared type: `GET /api/data-types`, `GET`/`DELETE /api/data-types/{type}/{id}`, and `POST /api/data-types/{type}/{id}/{trash,restore,retire}`. Permissions are per type, resolved in the handler against the same `RoleChecker` the middleware uses; an action is offered *only* when both its lifecycle support and its permission are declared, so a generated screen never renders a control the endpoint would refuse.
- `Whity\Core\Tenant\TableOwnershipRegistry` — a runtime, source-keyed map of which plugin owns which table, wired in both the HTTP and CLI entry points. A plugin may declare a data type or a referential guard only over tables it owns and that are tenant-scoped; core claims every table its own migrations create (`Whity\Core\Tenant\CoreTables`, pinned against the migrations by a drift test) before any plugin loads, so a plugin cannot claim one.
- Plugin SDK 1.16 — `Whity\Sdk\Rbac\PermissionResolver`: a read-only contract, registered in the service container by both the HTTP and CLI entry points, that lets a plugin ask the host for an authorization decision *inside* a handler instead of re-deriving it in hand-written SQL. It wraps the same delegation-aware `RoleChecker` the RBAC middleware enforces with, so the two can never give different answers to the same question. See [`docs/wiki/PERMISSION_SYSTEM.md`](docs/wiki/PERMISSION_SYSTEM.md).
- i18n admin management: `languages:manage` (create/update a language, system-tenant only) and `translations:manage` (create/update/delete a translation row) — `POST`/`PATCH /api/languages`, `GET`/`POST /api/translations`, `PATCH`/`DELETE /api/translations/{id}`. A translation row's tenant scope follows the System-Tenant Context convention: a regular tenant writes only its own override (a global/foreign row is 404), the system tenant writes only the system default (a per-tenant override is 422).
- Plugin marketplace: `whity-plugin-store` (in the companion `whity-plugins` repository) — a token-gated catalog server other Whity Core deployments can browse and install from.
- `POST /api/plugins/install-from-store` — fetch a plugin package from a trusted, allowlisted store and install it through the same hardened pipeline as a manual upload (SSRF-guarded).
- Admin **Plugin Store** page (`/admin/plugins/store`) — browse, search, and install plugins from a trusted store, with a token-mint convenience action.
- `plugins.store_allowed_hosts` global setting — the operator allowlist gating which store hosts are trusted for install-from-store.

### Fixed
- **A data-type restore silently discarded the record's prior state.** `POST /api/data-types/{type}/{id}/restore` wrote the type's declared `default_state` over whatever the record actually held before it was trashed, so a record trashed while `approved` came back `draft` — and the `200` reporting it (`"state":"draft"`) was indistinguishable from a correct undo. On any type with an approval gate that returned records to circulation looking unreviewed. The prior state was never unknown: `trash` already read it to publish as the transition hook's `from`, then dropped it. A restore now returns the record to the state it held. The state is kept in a new core-owned side table, `data_type_restore_states`, keyed `(tenant_id, data_type, record_id)` (migration 089) — **no plugin schema change and no plugin migration is required**, and core removes the row on a hard delete (`record_id` can carry no foreign key, since the target table varies by type) and once a restore has spent it. `default_state` is now documented as the FALLBACK, used when nothing was remembered (every record already in the trash when this shipped — the migration path) or when the remembered state is no longer one the type declares, including a state since repurposed as its `trashed_state` or `retired_state`. Reported by an adopter.
- **`\Whity\app(PermissionRegistry::class)` returned an empty permission catalogue instead of the populated one — silently.** Neither entry point registered the registry it built, filled and handed to the plugin loader, so the container's auto-instantiation fallback produced a fresh, *empty* one (concrete class, one *optional* constructor argument). A plugin asking whether its own declared permission existed was told `false`, denied access, and logged nothing: the failure was invisible at every layer. Both `public/index.php` and `BaseCommand::setupKernel()` now register the populated instance, and a real-boot test asserts the container returns the very object the loader filled — over HTTP and through the CLI kernel alike.
- **The container could improvise a stateful service.** Auto-instantiation was bounded by constructor *shape* ("concrete, no required arguments"), which is the wrong test: what matters is whether an improvised instance is distinguishable from a correct one, and for a registry it never is ("no permissions registered" is an ordinary answer). Two guards now stand where one did — the new `Whity\Core\Container\HostWiredService` marker, which opts a class out of auto-instantiation entirely regardless of its constructor (carried by `PermissionRegistry`, `ResourceTypeRegistry`, `HealthProbeRegistry`, `TableOwnershipRegistry`, `DataTypeRegistry`, `JobRegistry`, `TransportRegistry`, `PromptRegistry`, `LanguageRegistry`), and a fallback narrowed from "no *required* parameters" to "no parameters at all", since an optional constructor argument is a collaborator the host supplies rather than one the container may drop. Unregistered lookups of these classes now raise the documented, catchable `RuntimeException` naming the class instead of returning something plausible and empty.
- The CLI kernel did not register the `Database` service the HTTP host registers, so a plugin route reached through a `whity-cli` command failed on the documented `\Whity\app(Database::class)` seam (the constructor is private, so the lookup threw) while the identical route over HTTP served normally.
- The CLI kernel enforced a **different authorization policy** from the HTTP API: `BaseCommand::setupKernel()` built its `RoleChecker` without a delegation resolver, so a permission held only through a live, non-revoked delegation opened a route over HTTP and was invisible over the CLI. It now mirrors `public/index.php` exactly (delegation-unaware *bounding* checker for the no-transitive-re-delegation invariant; delegation-aware checker for enforcement).
- `\Whity\app()` raised an `\ArgumentCountError` — an `\Error`, so uncatchable via the documented `catch (\Exception)` — when asked for an unregistered service whose constructor takes arguments, turning a plugin's guarded lookup into a 500. It now reflects first and throws a catchable `\RuntimeException` naming the unwired service; auto-instantiation stays limited to concrete, argument-free classes so the container can never improvise a security service.
- `EnforceTenantIsolation` now exposes a narrow, anchored exemption for the plugin store's public read routes (catalog browse, registry index, token-gated download) without loosening any other route.
- Query-string parameters read via `parse_url($request->getPath(), PHP_URL_QUERY)` were silently empty at runtime (FrankenPHP strips the query from the request path) in `PersonsApiHandler` and the tenant-isolation query-based declared-target check; both now read `$_GET` as the runtime source.
- The Plugin Store admin page now surfaces the actual backend error message on a failed install or browse, instead of one generic message for every failure reason.
- Accessibility: `Input` now associates its label via `htmlFor` and sets `aria-invalid`/`aria-describedby` for validation errors; `Table` headers carry a `scope` attribute. See [`docs/wiki/A11Y.md`](docs/wiki/A11Y.md).

### Security
- **TOTP replay**: a captured valid 2FA code could authenticate a second, independent login within its validity window (`AuthHandler::handle2fa()` had no anti-replay state). Fixed with a per-profile anti-replay floor (`profiles.two_factor_last_used_step`, migration 080) atomically advanced on each accepted code, mirroring the existing backup-code single-use burn.
- **Refresh token reuse**: a stolen refresh token could be replayed to mint new token pairs indefinitely. Each successful refresh now immediately revokes the token it consumed (added to `revoked_tokens`); any later reuse of that same token is detected, logged as a security incident (`auth.refresh_token_reuse_detected`), and rejected with 401.
- **`ENCRYPTION_KEY` strength**: the documented ">= 32 chars outside development" convention (already enforced for `JWT_SECRET`/`RENDER_SHARED_SECRET`) was never actually checked for `ENCRYPTION_KEY` — only emptiness was rejected. New `EncryptionKeyGuard` closes the gap for both consumers (`TotpService::resolveEncryptionKey()`, `EncryptedSecretStore::fromEnv()`).
- Added `docs/wiki/Threat-Model.md` (STRIDE) and `docs/wiki/Pen-Test-Scoping-Brief.md` from an adversarial internal security audit; re-verified the tenant-isolation invariant across every table added since the prior 2026-07-20 investigation, with no drift found.
